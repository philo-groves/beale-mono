# Releasing Beale

Beale, app-server, and the two runtime packages advance together. The current coordinated candidate is `0.9.4`. A version number in source is not a published release. The macOS and Windows source installer clones the `release` branch and builds locally. Native installers with in-app updates are published by the Release workflow on a version tag.

## Change lanes

- Pull requests and pushes to `main` run `.github/workflows/ci.yml`: frozen install, version consistency, TypeScript build, fast suites, and Desktop production bundle.
- Before a release tag, run the **Release gate** workflow on the candidate commit from the Actions tab. It runs `pnpm release:verify` on macOS and Windows, including the hosted integration suites.
- A `vX.Y.Z` tag repeats the release gate. The tag must be annotated, match every package and release-facing version, point to the tested commit, and be reachable from `main`. The workflow only verifies; it does not publish or upload an installer.
- After merging verified source into `release`, zip the `website/beale-source-installer` directory and update the WordPress plugin on beale.ai. Check that `https://beale.ai/i` returns the exact `install.mjs` content before advertising the command. The same plugin redirects `/download/macos` and `/download/windows` to the matching assets in GitHub's latest published release. It caches the release lookup for five minutes and falls back to the latest release page if GitHub is unavailable or an expected asset is missing. Verify both links after publication.
- The same tag starts `.github/workflows/release.yml`. It runs `pnpm release:verify` on both operating systems, then waits for `release` environment approval before signing and packaging a macOS arm64 dmg and zip. When Windows signing is enabled, it also builds a Windows x64 NSIS installer. After artifact verification, the protected environment requires a second approval before publication. The release includes the `latest*.yml` update feed files and `SHA256SUMS.txt`.

Protect `main` with the CI `fast` check and require review before merging. The `v*` tag ruleset prevents updates and deletions; restrict tag creation to trusted maintainers as repository access expands. Enable immutable releases so published assets and their tags cannot be changed. Keep the release gate result attached to the exact candidate commit; rerun it after any candidate change.

## Prepare a candidate

1. Complete the candidate's numbered changelog section, grouped by Beale and app-server, and leave `## Unreleased` ready for subsequent changes. Describe migrations, compatibility requirements, and operator actions. Release notes use this section by default; if it exceeds GitHub's 125,000-character limit, add a concise `.github/release-notes/X.Y.Z.md` file that links readers to the full changelog. `release:check` validates the selected notes before tagging. Keep all examples synthetic and review the full diff for live workspace content and machine-local data.
2. For a new candidate version, run `pnpm release:version X.Y.Z`. This updates the five package manifests and the release-facing runtime identifiers. Keep independent managed plugin versions and the iOS repository's version on their own lifecycle.
3. Run `pnpm install --frozen-lockfile`, `pnpm release:check`, and `pnpm release:verify` locally. Live-provider tests are opt-in and require operator-supplied credentials.
4. Merge the candidate. Run the manual Release gate on the merged commit and review both OS results. Fix failures and rerun on the new commit.
5. Stop all app-server processes before taking a restorable backup of `~/.beale/memory.sqlite` and the affected research workspaces. Verify the backup can be read. Test any migration on a copy before upgrading an irreplaceable workspace.
6. Create an annotated `vX.Y.Z` tag on the verified commit and push it. Confirm the tag-triggered Release gate passes.

Do not treat a green source gate as installer validation. The Release workflow verifies the same tag on both operating systems before requesting approval to sign. Inspect the package jobs and downloaded artifact checks before approving publication.

## Installers and updates

`pnpm package:desktop` builds the workspace, stages the app-server runtime under `apps/desktop/build/runtime` (`apps/desktop/scripts/stage-runtime.mjs`), and runs electron-builder with `apps/desktop/electron-builder.yml`. Installed builds run app-server with Beale's own Electron binary, so they do not need a system Node.js. Windows launches the packaged tray host; macOS currently launches the packaged headless host.

Installed builds check the latest GitHub Release a few seconds after launch and every four hours. When a newer version exists, the header shows **Update to X.Y.Z**. The download starts only when the user clicks it, and **Restart Now** stops the local app-server and its restart supervisor before installing. While research sessions are active the app-server refuses to stop, so the restart waits and the button explains why. Updating Desktop does not update connected remote app-servers.

One-time repository setup:

- Create a `release` environment with required reviewers, restrict it to `v*` tags, and store macOS signing secrets and Windows signing variables there. The packaging jobs cannot access that environment until approval.
- For macOS, create a Developer ID Application certificate in the Apple Developer team and export its certificate and private key as a password-protected `.p12`. Add `MACOS_CERTIFICATE` (base64 of the `.p12`) and `MACOS_CERTIFICATE_PASSWORD` (its export password). Add the certificate's ten-character team identifier as the protected environment variable `MACOS_SIGNING_TEAM_ID`; keep its value out of the repository. The release job checks this identity, the app signature and notarization ticket, and the app inside both the DMG and ZIP. Keep the original `.p12` outside the repository and retain a secure backup; a certificate without its private key cannot sign a release.
- Have the Apple Developer Account Holder request App Store Connect API access; Apple reviews the request before team keys become available. Create a team API key with the minimum role needed for notarization. Add `APPLE_API_KEY` (the complete `.p8` contents), `APPLE_API_KEY_ID`, and `APPLE_API_ISSUER`. Apple offers the `.p8` for download only when the key is created. Keep it outside the repository and retain a secure backup. Do not use an individual API key with this workflow: the workflow requires a team issuer ID.
- For Windows, create a Microsoft Artifact Signing account, complete individual or organization public identity validation, and create a **Public Trust** certificate profile. For individual validation, Microsoft uses the legal name and address on the Azure billing account; verify they match the government ID before submitting. Register a dedicated Microsoft Entra application for CI. Give it a GitHub federated credential with issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`, and the exact subject GitHub issues for this repository's protected `release` environment. For GitHub.com repositories created after July 15, 2026, the default subject is `repo:OWNER@OWNER_ID/REPO@REPO_ID:environment:release`; confirm the format in GitHub's OIDC settings. Assign only the **Artifact Signing Certificate Profile Signer** role on that certificate profile. Do not create a client secret or export a signing private key for CI.
- In the protected `release` environment, set `WINDOWS_AZURE_CLIENT_ID`, `WINDOWS_AZURE_TENANT_ID`, `WINDOWS_AZURE_SUBSCRIPTION_ID`, `WINDOWS_SIGNING_ENDPOINT`, `WINDOWS_SIGNING_ACCOUNT`, `WINDOWS_SIGNING_PROFILE`, and `WINDOWS_SIGNING_PUBLISHER` as environment variables. The publisher value must exactly match the certificate's Common Name. Set `WINDOWS_SIGNING_ENABLED=true` only after the profile, federated credential, and role assignment are ready. When this flag is absent or `false`, the Release workflow skips Windows packaging; when it is `true`, incomplete configuration fails. The Windows packaging job alone can request GitHub OIDC tokens, after release-environment approval.

The Release workflow fails rather than publishing an unsigned installer when macOS credentials are missing or enabled Windows configuration is incomplete or invalid. It checks the Windows app and installer signatures, publisher, and timestamps. Before publication it checks the exact artifact filenames and confirms the update feeds reference those files with matching sizes and SHA-512 hashes. A local `pnpm package:desktop` build still requires local signing configuration; use the source installer for unsigned development setups.

Before the first public release, install the previous published build on each OS, publish the candidate, and confirm the in-app update relaunches into the new version, reconnects to app-server, and keeps workspaces intact.

## Recovery

If a candidate fails, fix it on a new commit and rerun the gate. Do not move an existing release tag. If an installed build fails after a data migration, stop app-server and restore the matching binary, global database, and workspace backup together. Older binaries are not assumed to read newer data. Document any migration or restore procedure in the release notes before distribution.
