# app-server

The app-server is the primary processing component of Beale. Each app client connects to one or more app-servers, and app-servers may also communicate with each other. The app-server runtime contains the full agent functionality to be shared across app clients.

Protocol v1.56 adds session token and cache telemetry totals to session detail. The host aggregates all saved main and subagent model calls, including turns older than the recent transcript. Cache-rate totals include only calls with reported cache-read tokens; missing cache telemetry stays unknown. SQLite schema 33 adds the nullable per-call cache-read count and migrates existing databases in place; older calls retain unknown cache telemetry. Protocol v1.55 added `total_duration_ms` and `has_campaign_activity` to session detail. The host derives the duration from all saved turns and the activity flag from successful campaign creation or graph delegation calls. The duration counts measured execution periods rather than idle time between turns. The turn stream emits an empty `SubagentsSpawned` event after graph assignments are validated and before they run.

Protocol v1.57 adds cumulative session usage snapshots at five-minute active-work intervals to session detail. SQLite schema 34 stores each new model call's offset within its turn; existing calls without an offset appear at their completed-turn boundary. The final partial interval is included.

## First Rust slice

On Windows, `serve` shows a Beale notification-area icon with a running-status tooltip and an **Exit** menu action. Exit gracefully stops the HTTP listener and removes the icon. Ctrl+C remains available in the terminal. Other platforms continue to use terminal shutdown.

`beale-core` is a runnable host that assembles the provider, workspace, session, permission, and plugin routes. `beale-storage` owns the host SQLite schema and typed storage operations. `beale-workspaces` owns workspace validation, registry and manifest operations, and workspace routes; `beale-sessions` owns session operations and routes and depends on the workspace store for workspace membership. `beale-tools` owns the four base host tools and bounded result helpers. `cargo run -p beale-core -- serve` binds `127.0.0.1:43831` by default and serves `GET /v1/health` as `application/x-protobuf`. Set `BEALE_V2_APP_SERVER_ADDR` to another loopback IP and nonzero port when needed; non-loopback bindings are rejected. The desktop uses the same address and validates the service name and protocol version. The v1.57 contract includes authenticated local provider operations, workspace reads and edits, session and Quick Chat turns, archive listing and restoration, permission rule reads, edits, and creation, plugin listing, installation, uninstallation, manifest reads, and workspace scope updates, a framed live session stream, compact tool summaries, positioned reasoning and commentary, separate paged tool detail, a Fleet peer descriptor, and Tracking history. Its protobuf schema is `beale-contracts/proto/beale/v1/host.proto`; the matching Rust `prost` type is kept in source because the bundled Windows `protoc` cannot run in this development environment. The app-server creates a random control token in its private host directory, which the same-device desktop reads for local operations. The host remains bound to loopback; operators can expose it through Tailscale Serve HTTPS. Client-to-host WebSockets are not part of this transport. See the [workspace run instructions](../../README.md) for the two-process flow.

`beale-extender` owns the plugin catalog, installation registry, and MCP server lifecycle. Authenticated `GET /v1/plugins` returns validated package summaries, exact Skills and MCP Servers counts, and saved install state; `POST /v1/plugins/manifest` returns a selected package's validated `plugin.json` on demand. `POST /v1/plugins/install` and `POST /v1/plugins/uninstall` set or clear that state idempotently by plugin name. The four shipped Agent Plugins packages and user-supplied packages under `~/.beale/v2/plugins/packages/<plugin-name>/` (or `BEALE_V2_HOME/plugins/packages/<plugin-name>/`) can use these routes. The directory name must match `plugin.json` name. SQLite schema 11 adds the install registry and migrates existing host databases in place. Installed MCP servers launch on install or first plugin listing after app-server start. Their paginated `tools/list` results replace bundled tool estimates; a failed server contributes zero tools and does not stop other servers. Stdio and Streamable HTTP are supported, including the older MCP initialization handshake. Uninstall stops active stdio servers. Skill and MCP tool exposure to sessions remains separate, and Git source import is not implemented.

Session summaries include the time of the last saved message. SQLite schema 12 adds this timestamp; existing sessions initialize it from creation time, and subsequent turns update it transactionally.

Goal Mode is an optional `beale-core` Cargo feature enabled in the default build. Its implementation lives in `extensions/features/beale-goals`; the session harness supplies the narrow tool and continuation hooks. A new session opts in through the v1.29 turn request. Max turns and max active-work duration in minutes are optional; zero means unlimited for each. Active duration accumulates completed turn times and excludes time waiting for a user or external change. The host checks limits after each completed turn. It appends Goal Mode guidance to the system prompt, exposes `goal_status`, and continues after a `continue` signal until the model records `achieved`, names a concrete external state to wait for, omits a valid signal, is interrupted, or reaches a configured limit. Each turn is saved before the next begins. The stream sends intermediate `TURN_COMPLETED` details so the desktop can show progress. SQLite schema 13 stores goal status and marks generated continuation prompts as internal; schema 14 adds limits and accumulated work time, defaulting existing goals to unlimited. Providers receive internal prompts in context, while clients see only real user messages. Recent turns are supplied to the provider and desktop from a bounded window; earlier turns remain in SQLite. Session execution is serialized per session, leaving other sessions and Quick Chats available during long goals. A new user message resumes a waiting or paused goal unless a configured limit was reached. Builds without `goal-mode` reject new Goal Mode requests and leave saved goal state intact.

Protocol v1.30 adds authenticated feature listing and enablement routes. SQLite schema 15 stores feature state and pauses previously active goals during migration; Goal Mode is disabled until explicitly enabled in the Features view. Disabling it pauses active goals after their current turn and prevents new Goal Mode sessions. The host owns the feature catalog routes; each native feature supplies its metadata and optional implementation from its own crate. Builds without `goal-mode` omit Goal Mode from the catalog and reject new Goal Mode requests. Fleet is compiled by default through the separate `fleet` Cargo feature, but its saved state starts disabled.

Protocol v1.37 adds Fleet app-server descriptors and authenticator pairing. Authenticated local provisioning returns an `otpauth` URI for a QR code; the 20-byte secret persists in SQLite schema 17. A same-tailnet desktop can submit a current six-digit TOTP code over Tailscale Serve HTTPS to pair, with in-process replay rejection and exponential backoff after failed attempts. The remote host then returns its control token over the verified HTTPS connection. Builds without `fleet` omit these routes. The desktop owns saved remote connections; session routing to remote app servers remains separate. Protocol v1.38 adds authenticated browser inventory and manual add/remove routes. Each host probes conventional browser installation paths and stores manual executables in SQLite schema 18. Browser paths stay on the host. Protocol v1.39 adds authenticated browser setting updates and returns enabled state and workspace scope with inventory; SQLite schema 19 saves those settings. Existing browsers default to enabled for all workspaces. Protocol v1.40 marks the host's preferred browser and adds an authenticated choice update; SQLite schema 20 saves the explicit choice. Until one is saved, the host prefers its OS default browser when present and enabled, then falls back to an enabled browser.

Protocol v1.41 adds an authenticated, read-only Virtual Machines inventory. On Windows, the host runs the local Hyper-V `Get-VM` query with a fixed command and returns bounded VM IDs, names, states, and generations. Hosts without Hyper-V return an empty list; an installed host that cannot be queried returns an inventory error. VM paths and configuration do not cross the API.

Protocol v1.47 adds graph node model choices and per-role Max Concurrent values to the first session turn and session detail. The optional `beale-graphs` crate defines Simple Orchestra with one main agent and a single Scout, Reviewer, and Prover layer. The main role accepts one model and has a fixed concurrency maximum of 1; subagent limits remain optional. Graphs is disabled by default, and the host accepts the graph only when the feature applies to the chosen workspace. SQLite schema 26 saves the graph configuration with the first turn; existing graph selections retain their graph ID and model choices. When enabled, Simple Orchestra adds a manager-controlled delegation tool to the main agent. Each batch runs up to eight independent role assignments in fresh contexts, with at most 16 assignments per turn and the saved per-role concurrency limit. Subagents use their configured provider and model, the same reviewed base tools, and bounded result pagination; they cannot delegate. Their tool calls are retained with the session turn. The main agent receives their results and owns the final response. No Graph leaves the graph ID empty and runs only the main agent.

Protocol v1.44 adds authenticated automation run status alongside listing and cancellation. The first completed session turn with a Repeat preset records a job and its initial run. SQLite schema 23 saves the options needed for later occurrences. The host claims due jobs, runs each occurrence in a new session, and records completion or failure. A stopped host skips old missed occurrences when it resumes. The desktop can skip the next planned occurrence or cancel the series.

Protocol v1.42 adds an authenticated VM settings update and returns enabled state, workspace scope, Can Run, and Can Clone in inventory. SQLite schema 21 saves these per VM ID. Newly detected VMs start enabled for all workspaces, while both access allowances start off. The host accepts settings only for a VM still in its local inventory; these fields do not start or clone a VM.

Protocol v1.31 marks whether each feature provides a system-prompt extension. Goal Mode supplies its prompt section only during active goal turns.

Protocol v1.32 adds an authenticated, on-demand feature-details route. Goal Mode returns its fixed prompt extension; live turn limits and progress remain appended by the harness when an active goal runs.

Protocol v1.33 adds model-facing tool counts to the feature catalog. Goal Mode contributes one `goal_status` tool while active.

Protocol v1.34 adds the MCP tool count to each Plugin summary. Available bundled cards use a source inventory; installed cards use live server discovery.

Protocol v1.35 adds workspace scope to Plugin and Feature summaries and authenticated `POST /v1/plugins/scope` and `POST /v1/features/scope` updates. Installed Plugins and enabled Features default to All Workspaces. The scope can be any selected subset or No Workspaces; selecting All Workspaces resets it. SQLite schema 16 persists this choice, validates workspace IDs against the registry, and removes deleted workspace IDs without expanding a restricted scope to All Workspaces. Goal Mode checks its scope before a session starts or resumes and pauses active goals outside a changed scope. Plugin MCP tools and Skills are not yet exposed to sessions, so Plugin scope is saved for their later integration.

`beale-safety` owns the host-saved Auto-Review and Guardian rule catalog. Before `read`, `write`, `edit`, or `bash`, the selected small provider model reviews enabled Auto-Review rules. The session lead model revisits a completed denial when Guardian rules are enabled. Invalid or unavailable reviews deny the tool call. Each rule's name, instruction, and enabled state can be edited through authenticated `GET` and `PUT /v1/permissions/rules`. Authenticated `POST` creates a rule in either stage with a host-assigned ID, enabled by default. The catalog is limited to 16 rules. Rules are stored in the host SQLite database; schema 10 adds stage and ordering fields for custom rules while preserving earlier rule settings. These model reviews do not provide OS isolation.

`POST /v1/workspaces` accepts a protobuf `CreateWorkspaceRequest` with a name, operator-selected absolute directory, optional guidance, optional typed surfaces, and rules. `GET /v1/workspaces` returns saved workspace summaries; `GET /v1/workspaces/{id}` returns workspace details from the host-owned manifest and guidance file. All require the local control token. The host requires an empty dedicated directory, rejects duplicate surface identities and existing workspace paths, and never adopts existing directory content. A successful create writes schema 5 `workspace.json`, `AGENTS.md`, `.beale/`, and the standard research directories, then registers the workspace in the host SQLite database. Existing schema 3 and 4 manifests migrate on read and persist as schema 5 on the next write.

Custom Instructions import validates the model's complete draft before workspace creation. If the draft fails, the host requests a corrected JSON draft up to two times. Surface parent and relationship references must resolve to explicit temporary keys. An in-scope surface propagates scope to descendants only with a recorded scope basis; an unsupported model-supplied propagation flag is cleared. Invalid references and authorization conflicts are still rejected.

`GET /v1/workspaces/{id}/campaign`, `/foundation`, `/surfaces`, and `/rules` have separate response types. Campaign currently returns no enabled features. `PUT` on Foundation, Surfaces, and Rules accepts only that section's fields and its expected revision, returns the saved section with its next revision, and rejects stale revisions with `409`. Existing schema-v3 workspaces without revision fields begin at revision 1. The host keeps the workspace directory fixed, allows an empty surface list, preserves creator tags and exclusion reasons for unchanged surfaces, and records whether new surfaces came from the operator, an import, or an agent tool. The aggregate `GET /v1/workspaces/{id}` remains available for older v1.7 clients.

Creation writes to an empty operator-selected directory and does not delete it on a filesystem failure. A failed operation can therefore leave a partial directory that must be inspected before retrying; the host will not adopt it as a new workspace.

`beale-providers` owns host-only OpenAI, xAI, Anthropic, Z.ai, OpenRouter, and custom API-provider credentials and text inference. Built-in API-key requests use a saved host key when configured, falling back to the corresponding `OPENAI_API_KEY`, `XAI_API_KEY`, `ANTHROPIC_API_KEY`, `ZAI_API_KEY`, or `OPENROUTER_API_KEY` environment variable. Subscription requests use OpenAI's direct Responses API or xAI device authorization and the Grok Build chat proxy. The xAI proxy requires a client-version header for text turns. The xAI subscription device client ID currently matches the one used by v1; it is isolated in the OAuth module for replacement with a Beale-specific registration. Provider routes centralize endpoint and wire-shape choices so additional adapters can be added without changing the host contract. API-key inference routes stream upstream responses and require a terminal success event. The Anthropic and Z.ai subscription adapters use official CLI turns with structured tool decisions; they currently deliver each step when the CLI completes it. Model IDs are supplied by the caller instead of pinned in code. The host lists account-available text models through the same credential path used for inference, recommends lead and small choices from that list, and stores selected defaults separately for each provider and sign-in method. OpenAI model display names replace dashes with spaces; model IDs remain unchanged. A default save is checked against a fresh provider catalog. A saved choice that disappears from the catalog falls back to an available model. The current recommendations prefer OpenAI GPT-6.1 Sol and GPT-6 Luna, or xAI Grok 4.7 and an available fast variant; actual selections depend on account availability.

Anthropic uses the Messages API with streamed text and tool-use blocks. Z.ai and OpenRouter use chat completions; OpenRouter model IDs keep their provider prefix. Custom providers have host-owned definitions and optional protected keys, use a configured OpenAI-compatible `/chat/completions` endpoint, and retain provider-qualified model IDs in saved sessions. The custom registry and credential operations are authenticated local protobuf routes. OpenAI and xAI retain subscription sign-in. Anthropic subscription turns use the official Claude CLI with its direct tools disabled; Z.ai subscription turns use the official ZCode app-server protocol with no delegated tools. The Rust harness executes requested Beale tools and retains session history; neither adapter copies subscription tokens. ZCode on Windows and macOS needs the installed ZCode bundle and Node on PATH. OpenRouter and custom providers use API keys. Live provider tests require operator credentials and remain opt-in.

From `beale-v2/`:

```text
cargo run -p beale-core -- serve
cargo run -p beale-core -- login-openai
cargo run -p beale-core -- login-xai
cargo run -p beale-core -- infer openai subscription <model> < prompt.txt
cargo run -p beale-core -- infer xai api-key <model> < prompt.txt
```

Sign-in prints a provider URL or device code and saves OAuth credentials under the current user's `.beale/v2` directory (or `BEALE_V2_HOME`). On Unix files are created with mode `0600`; on Windows the host sets a user-only file ACL before replacing a saved record. API keys are read from the host environment and are never written by these commands. `infer` reads the prompt from standard input. Live provider calls require user-provided credentials and have not been exercised by the automated tests.

The CLI is a local provider verification path. This slice stores one OAuth registration per provider; account selection is not implemented. The app-server has an authenticated local session turn endpoint with completed-turn and tool-call storage in its host database. Remote client authentication and a Tailscale listener remain unimplemented.

The app-server stores source priority per provider in its private database. Subscription is the default when both credentials are configured; an explicit API Key choice is retained across restarts. If only one credential is configured, the desktop uses that source for model settings. The app-server stores the lead provider in the same database. The first provider configured becomes lead, and adding another provider leaves the choice intact. A local client may select another configured provider. Removing the lead provider's last credential reassigns lead to an available provider, or clears it when none remain. If both providers were configured before this setting existed, the app-server uses OpenAI as the initial fallback because their original add order was not recorded.

The OpenAI-only Daybreak Mode setting appears in provider status and accepts Blue or Red through authenticated `POST /v1/providers/openai/daybreak-mode`. Blue is the default; an explicit Red choice is stored in the private host database. Every OpenAI Responses request, including Quick Chat and tool rounds, sends `access_programs.cyber`. The host selects `daybreak_blue` for general-purpose models and `daybreak_red` for known Red cyber models; GPT-6.1 Sol and GPT-6 Astra require Red approval but still send `daybreak_blue`. The Blue-mode model catalog excludes known Red-required models, and a request for one fails before the provider call with a specific error. Unknown models request `daybreak_blue` and may be rejected by the provider if unsupported. This follows [OpenAI's model-specific Daybreak rules](https://developers.openai.com/api/docs/guides/daybreak). New OpenAI lead defaults prefer GPT-5.6 Sol when available; existing saved choices remain in place.

OpenAI inference and tool turns use the Responses WebSocket with `store: false`. Within a tool loop, the host sends only new items with the previous response ID on the same connection. On a lost connection or missing response ID, it reconnects once and replays host-held input; a second interruption fails the turn. Requests enable server-side compaction at 100,000 tokens, preserve encrypted reasoning and compaction output for later turns, and discard earlier items only after a compaction item is saved. SQLite schema 24 stores that replay context with each completed session turn. OpenAI tools are grouped in a `beale` namespace for subscription compatibility. The host combines terminal response output with finished output-item events by index so tool calls are retained even when the terminal output array is empty.

Session routes require the local control token. GET /v1/sessions lists unarchived saved sessions, GET /v1/sessions/{id} returns a transcript with compact tool descriptions, POST /v1/sessions/{id}/archive archives a session, and POST /v1/sessions/{id}/restore returns it to workspace lists. GET /v1/archive returns bounded titles, models, workspace IDs, turn counts, and timestamps for archived sessions and Quick Chats. POST /v1/sessions/turns runs a turn through the chosen provider and credential method. GET /v1/sessions/{id}/tools/{tool_id}?offset=N fetches that tool's arguments and up to 8,000 bytes of retained output. The host stores full tool output up to 8 MB per call, bounded reasoning and commentary, and turn duration in SQLite; schema 7 adds session archive timestamps and migrates earlier schemas in place. For model context, large results send an 8 KB head/tail preview and a `tool_result_page` pointer so the model can fetch omitted pages. `read`, `write`, `edit`, and `bash` are the only base tools. Bash uses the user's host privileges and has a 60-second runtime limit; the app-server does not provide OS isolation. A new session is saved after a provider response, or after tool activity if the provider stops before completion; the latter turn records an interruption message. Session history is local to the app-server and bound to a registered workspace.

`POST /v1/quick-chats/turns` accepts an optional chat ID, bounded prompt, and optional selected workspace ID, then returns the saved title and user/assistant transcript. The host selects its configured lead provider, source priority, and lead model for the first turn; later turns keep that selection. Quick Chats use a reserved internal session identity and are archived when first saved, outside workspace session lists. A selected workspace contributes saved guidance, rules, and scope to the system prompt, with no file tools; the host validates the workspace and binds its ID to the chat in SQLite schema 6. Existing no-workspace Quick Chats migrate with an empty binding, and schema 7 archives existing saved Quick Chats. Authenticated GET /v1/quick-chats/{id} reloads a saved chat for desktop restoration; the active chat is hidden from the Archive list until closed.

The v1.13 session contract forwards the selected reasoning effort to OpenAI Responses turns. The v1.12 session contract added positioned reasoning summaries, intermediate assistant text, turn duration, and a live turn stream. `POST /v1/sessions/turns/stream` returns `application/x-beale-protobuf-stream`: each `SessionStreamEvent` is protobuf encoded behind a four-byte big-endian length. It sends provider text and available summary deltas as they arrive, tool start and finish events, then a completed `SessionDetail` or a bounded failure. The prior completed-turn endpoint remains available. Tool arguments and output stay host-only until requested through the detail route. OpenAI Responses requests opt into summaries; xAI Responses summaries are retained when supplied. The xAI subscription chat adapter omits raw reasoning content and currently has no summary field to forward. Raw reasoning text is never sent to clients. SQLite schema 5 stores bounded summaries, intermediate text, and turn durations, migrating existing schema-1 through schema-4 sessions in place.

## System prompt

The app-server creates `~/.beale/v2/SYSTEM.md` on startup if it is missing (or `SYSTEM.md` beneath `BEALE_V2_HOME`). It preserves existing edits and rereads the file at the start of each session turn, so changes apply without a restart. The file contains the base Markdown instructions, including base-tool guidance. Future optional tool and plugin details can be appended in memory for the provider request. There are no placeholder variables or template substitutions. The prompt file is limited to 64 KiB, and the composed prompt to 96 KB. Workspace guidance and rules are not yet appended.

Subscription usage is available through authenticated GET /v1/providers/usage. The host caches snapshots for five minutes and returns only bounded percentages and reset times. OpenAI's circle reads an existing Codex sign-in from ~/.codex/auth.json (or APP_SERVER_CODEX_AUTH_FILE / BEALE_OPENAI_CODEX_AUTH_FILE); Beale's token-sharing OpenAI sign-in cannot currently query plan usage. xAI's circle uses the host's xAI subscription credential. Unavailable windows are omitted.

Tracking is an optional native feature in `extensions/features/beale-tracking`, disabled by default. When enabled, authenticated `GET /v1/tracking` returns at most seven days of observed subscription windows and daily aggregates of Beale research-session model calls. Schema 27 stores subscription samples and per-call main or subagent identifier, role, model, duration, and provider-reported token counts. Samples are collected only when provider usage is checked while the host runs; earlier history is not backfilled. Calls without reported token counts retain duration and are counted as unmeasured for token totals. The route is host-wide and cannot be scoped to individual workspaces.

The Surfaces feature is compiled into the default host build but disabled in saved feature state until enabled for a workspace. It supplies four model tools: `surface_add`, `surface_edit`, `surface_get`, and `surface_query`. When disabled, sessions and Quick Chat omit surface records from model context and sessions omit these tools. Workspace rules remain available for general authorization boundaries. Surface definitions are optional during workspace creation; a workspace without an in-scope surface must record at least one Rule. Schema 5 manifests record per-surface creation and update times plus revision changes with before and after values; deleted surfaces remain as historical records. Old progress fields are ignored and cleared when manifests are written; historical edits before schema 5 are not reconstructed.

The optional Knowledge Base feature is disabled by default and can be scoped to workspaces. It stores memories and security claims as separate record kinds in the app-server database, with workspace-local M and C IDs, evidence, links, duplicate relationships, and revision history. Memories can describe a sink, source, invariant, control, trust boundary, observation, method, prior art, or negative result without becoming findings. A claim starts as a lead or an observed finding; observed status requires a durable successful read or bash tool result from the same workspace. Knowledge records only the cited current-turn tool result as a durable host receipt. The feature does not depend on Runbooks, Graphs, Surfaces, or Reporting. Reproduced and verified transitions remain unavailable until Knowledge owns a verifier that can validate their evidence. Authenticated JSON routes `POST /v1/knowledge/query` and `/get` provide bounded catalog and paged-history detail reads; their DTOs live in `beale-contracts::knowledge`. Host database schema 31 and protocol v1.53 add this contract.
