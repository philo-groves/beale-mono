# app-server

The app-server is the primary processing component of Beale. Each app client connects to one or more app-servers, and app-servers may also communicate with each other. The app-server runtime contains the full agent functionality to be shared across app clients.

## First Rust slice

`beale-core` is a runnable host. `cargo run -p beale-core -- serve` binds `127.0.0.1:43831` by default and serves `GET /v1/health` as `application/x-protobuf`. Set `BEALE_V2_APP_SERVER_ADDR` to another loopback IP and nonzero port when needed; non-loopback bindings are rejected. The desktop uses the same address and validates the service name and protocol version. The v1.8 protobuf contract includes authenticated local provider operations and workspace creation, listing, and section-specific reads and edits. Its schema is `beale-contracts/proto/beale/v1/host.proto`; the matching Rust `prost` type is kept in source because the bundled Windows `protoc` cannot run in this development environment. The app-server creates a random control token in its private host directory, which the same-device desktop reads for local operations. No remote listener or client inference operation is exposed yet. Client-to-host WebSockets are not part of this transport. See the [workspace run instructions](../../README.md) for the two-process flow.

`POST /v1/workspaces` accepts a protobuf `CreateWorkspaceRequest` with a name, operator-selected absolute directory, optional guidance, typed in-scope/out-of-scope surfaces, and rules. `GET /v1/workspaces` returns saved workspace summaries; `GET /v1/workspaces/{id}` returns bounded workspace details from the host-owned manifest and guidance file. All require the local control token. The host requires at least one in-scope surface and an empty dedicated directory, rejects duplicate surface identities and existing workspace paths, and never adopts existing directory content. A successful create writes schema-v3 `workspace.json`, `AGENTS.md`, `.beale/`, and the standard research directories, then adds the workspace to the host-owned `workspaces.json` registry under `BEALE_V2_HOME` (or `~/.beale/v2`). Schema 3 keeps these new workspaces distinct from the v1 schema-1/2 formats. The host marks initial surfaces as user-created and records "Set at workspace creation" for exclusions.

`GET /v1/workspaces/{id}/campaign`, `/foundation`, `/surfaces`, and `/rules` have separate response types. Campaign currently returns no enabled features. `PUT` on Foundation, Surfaces, and Rules accepts only that section's fields and its expected revision, returns the saved section with its next revision, and rejects stale revisions with `409`. Existing schema-v3 workspaces without revision fields begin at revision 1. The host keeps the workspace directory fixed, requires an in-scope surface, preserves creator tags and exclusion reasons for unchanged surfaces, and marks newly added surfaces as user-created. The aggregate `GET /v1/workspaces/{id}` remains available for older v1.7 clients.

Creation writes to an empty operator-selected directory and does not delete it on a filesystem failure. A failed operation can therefore leave a partial directory that must be inspected before retrying; the host will not adopt it as a new workspace.

`beale-providers` owns host-only OpenAI and xAI credentials and text inference. API-key requests use a saved host key when configured, falling back to `OPENAI_API_KEY` or `XAI_API_KEY`, and call the providers' Responses endpoints. Subscription requests use OpenAI's Sign in with ChatGPT flow on the public Responses API or xAI device authorization and the Grok Build chat proxy. The xAI subscription device client ID currently matches the one used by v1; it is isolated in the OAuth module for replacement with a Beale-specific registration. Provider routes centralize endpoint and wire-shape choices so additional adapters can be added without changing the host contract. Inference routes stream upstream responses and require a terminal success event. Model IDs are supplied by the caller instead of pinned in code. The host lists account-available text models through the same credential path used for inference, recommends lead and small choices from that list, and stores selected defaults separately for each provider and sign-in method. OpenAI model display names replace dashes with spaces; model IDs remain unchanged. A default save is checked against a fresh provider catalog. A saved choice that disappears from the catalog falls back to an available model. The current recommendations prefer OpenAI GPT-6.1 Sol and GPT-6 Luna, or xAI Grok 4.7 and an available fast variant; actual selections depend on account availability.

From `beale-v2/`:

```text
cargo run -p beale-core -- serve
cargo run -p beale-core -- login-openai
cargo run -p beale-core -- login-xai
cargo run -p beale-core -- infer openai subscription <model> < prompt.txt
cargo run -p beale-core -- infer xai api-key <model> < prompt.txt
```

Sign-in prints a provider URL or device code and saves OAuth credentials under the current user's `.beale/v2` directory (or `BEALE_V2_HOME`). On Unix files are created with mode `0600`; on Windows the host sets a user-only file ACL before replacing a saved record. API keys are read from the host environment and are never written by these commands. `infer` reads the prompt from standard input. Live provider calls require user-provided credentials and have not been exercised by the automated tests.

The CLI is a local provider verification path. This slice stores one OAuth registration per provider; account selection is not implemented. The app-server currently has no client-facing inference endpoint, agent runtime, durable research storage, remote client authentication, or Tailscale listener. These boundaries need their own contracts before they are connected.

The app-server stores source priority per provider in its private host directory. Subscription is the default when both credentials are configured; an explicit API Key choice is retained across restarts. If only one credential is configured, the desktop uses that source for model settings. The app-server stores the lead provider in its private host directory. The first provider configured becomes lead, and adding another provider leaves the choice intact. A local client may select another configured provider. Removing the lead provider's last credential reassigns lead to an available provider, or clears it when none remain. If both providers were configured before this setting existed, the app-server uses OpenAI as the initial fallback because their original add order was not recorded.

The OpenAI-only Daybreak Mode setting appears in provider status and accepts Blue or Red through authenticated `POST /v1/providers/openai/daybreak-mode`. Blue is the default; an explicit Red choice is stored in the private host directory. The current generic provider inference path does not use this choice yet: [OpenAI's access marker depends on the requested model](https://developers.openai.com/api/docs/guides/daybreak), so applying a mode to every request would be incorrect.
