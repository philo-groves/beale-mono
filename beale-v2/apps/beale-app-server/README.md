# app-server

Surface tools describe the supported surface types and locator combinations and report invalid choices directly. A threat model scenario can be saved with `review_mapping: true` to mark the current mapping revision reviewed in the same edit. Auto-Review receives a compact inventory of every recorded surface ID, scope state, type, and bounded locator, along with workspace guidance and rules; verbose surface descriptions and relationships remain in agent context. A transient provider connection or response-body interruption is retried once for the current model step before the turn is saved as interrupted.

The host writes timestamped diagnostics to `logs/app-server.log` beneath `BEALE_V2_HOME` or `~/.beale/v2` and prints the path at startup. The file rotates at 5 MiB with three backups; errors also appear on stderr. The log directory and files are restricted to the current user. Review local paths in logs before sharing them.

Long graph turns persist all model usage rows and child transcripts without a fixed per-turn model-call or transcript-size quota. Non-OpenAI conversations can exceed 192 input items; provider context limits still apply at the provider. If a turn cannot be committed, the host logs the storage error. OpenAI WebSocket 403 responses produce a specific account or model access message, and permission review denials continue to block the requested tool. Disabled review rules allow approved tools to continue. Graph subagents report missing scope details in their result for the parent to resolve.

Protocol 2.22 adds top-level role usage, saved subagent summaries and authenticated child transcript reads, plus live child lifecycle and activity events. Protocol 2.21 streams one usage delta after each completed provider call so open sessions can update token totals before a turn is saved. The desktop folds these deltas into its session sidebar and Insights view, then uses saved detail when an agent turn completes. Rebuild and restart the host and desktop together.

Both Research Pipeline variants start with an Audit Targets peer that maps diverse authorized codebase scopes, ranks them by reachability, sinks, code smells, historical precedent, and related weakness indicators, and hands an ordered, evidence-linked `ranked_targets` list to Discovery. The host validates the ranking signals and retains the list in the durable handoff. Concurrent runs start recipients as handoffs arrive. Sequential runs use one top-level agent at a time, with a saved stage duration (default 60 minutes), a soft system reminder at the deadline, a hard stop ten minutes later, and requeueing of interrupted handoffs. Downstream roles advance when their finding queues empty; Patch Generation cycles back to Audit Targets. Protocol 2.23 carries the stage duration in the request and session detail. Discovery researches those targets for Candidate findings and hands testable hypotheses to validation. Validation owns focused PoCs and evidence-backed Validated completion; Reporter owns screening and reporting. The host rejects finding stage changes from the wrong top-level role. Successful read and bash results include the exact finding evidence reference. A permission review service failure retries one transient provider error, timeout, or invalid response with a 45-second attempt limit; if review still cannot complete, the tool stays blocked, its saved result names a safe failure category, and the affected turn stops with completed activity retained. If Guardian is unavailable after a valid Auto-Review denial, that denial stands and the agent may continue other work. Unreviewed calls in that response receive explicit not-run results before OpenAI context is saved; older incomplete context is repaired on replay.

OpenAI subscription inference reads the host Codex sign-in and uses the Codex Responses backend. Its model catalog is local, as in v1, so model lookup does not depend on OAuth refresh or a remote catalog. Saved lead and small choices remain subject to the active Daybreak mode.

OpenAI subscription permission reviews use the active research model so a separate small-model access denial does not block tools. Provider reasoning summaries are bounded for display without aborting an otherwise valid response. Interrupted turns retain completed tool activity and show the sanitized provider cause. Daybreak response checks report the requested and selected program; a mismatch still stops the affected provider step.

Protocol 2.20 adds an authenticated Stop route for a running streamed turn. The desktop sends a unique turn ID in the stream request and can stop that turn without disconnecting the stream; the host saves completed activity and pauses an active goal. Canceling an automation series also stops its active run. Rebuild and restart the host and desktop together.

Protocol 2.19 adds top-level agent and handoff state to session detail and streams agent start and completion events. SQLite schema 46 gives new peer graph sessions separate role turns and a durable handoff queue; schema 47 saves provider context per top-level agent so work can continue across turns without mixing roles. The host runs distinct roles concurrently and serializes work within each role; roles without work stay idle. Agents continue through tool work until they finish, fail, or the user stops them; explicit Goal Mode limits still apply. After restart, interrupted handoffs return to the pending queue and the next session turn resumes them. Earlier shared-turn graph sessions retain their original behavior. Protocol 2.18 tagged streamed and saved graph activity by role and added a bounded live tool-detail page; schema 45 added role columns to tool, reasoning, and commentary rows. Bash commands default to a 120-second timeout and may request up to 600 seconds. Rebuild and restart host and desktop together.

When the optional Agent Feedback feature is enabled for a workspace, the main session agent can load its single `agent_feedback` tool, and graph subagents receive the same tool, to report a concrete Beale harness or agent runtime flaw, quirk, or limitation. Reports append to `agent-feedback.jsonl` beneath `BEALE_V2_HOME` or `~/.beale/v2`, with a user-only file ACL or mode. Developers can read the file directly, for example with `Get-Content "$env:USERPROFILE\.beale\v2\agent-feedback.jsonl"` on Windows. The tool result does not repeat the report, and no client viewer or API route is added.

Graph subagent activity carries a child ID and stays in its own transcript view. Saved child summaries appear in session detail; an authenticated, paged subagent detail route returns the retained child messages, reasoning, and tool summaries.

Memories is an optional workspace feature, disabled by default. It provides four read-only model tools: `memory_session_query`, `memory_query`, `memory_read`, and `memory_graph`. The session query reads saved messages, tool calls, commentary, and available reasoning summaries from the existing `state.sqlite` transcript. Schema 44 adds child transcript items and an ordered, durable turn-end outbox in that database. A host worker reads each queued turn after commit and asks the configured default small model for bounded entities and assertions. Validated proposals update `~/.beale/v2/memories.sqlite` in one transaction with a processed-job marker, evidence references, temporal fields, model authorship, and revision history. Failed jobs retry with backoff and become visible as failed after five attempts. When Memories is enabled, a small relevant selection is added to each turn as sourced data. Protocol 2.12 adds authenticated `POST /v1/memories/status`, `/retry`, and `/clear`; clear requires the feature to be disabled for that workspace, deletes its queue and memory records, and leaves transcripts intact.

The app-server is the primary processing component of Beale. Each app client connects to one or more app-servers, and app-servers may also communicate with each other. The app-server runtime contains the full agent functionality to be shared across app clients.

Updating root cause or attack path invalidates screening; changing scores also requires screening again. JSON records gain these fields without a database migration. Existing completions and history are preserved; absent scores remain unrated and are not backfilled. Rebuild and restart host and desktop together.

Desktop Insights uses these session-scoped values independently of host-wide Tracking. Rebuild and restart host and desktop together.

Runbook create and edit tools limit newly supplied titles to 64 characters. The host still accepts edits that leave an older, longer title unchanged.

## Storage

The host database is `state.sqlite` beneath `BEALE_V2_HOME` or `~/.beale/v2`. Each schema owner records its own version in `schema_versions`. The `host` owner (in `beale-storage`) holds workspaces, sessions, turns, tool calls, reasoning and commentary, subagent transcripts, model usage, provider context, Quick Chat bindings, provider settings, permission rules, plugin installs, feature and extension scope state, and automations. Each native feature owns its tables and applies its migrations under its feature ID when the host starts: Findings, Runbooks, Fleet, Tracking, Goal Mode, Memories (the extraction queue; extracted memories stay in `memories.sqlite`), and Graphs (graph selection, peer turn reservations, and handoffs). Optional feature tables are absent when that feature is omitted from the build; Goal Mode, Fleet, and Tracking tables remain available in every build. Feature rows that must be saved atomically with a turn, such as Goal Mode progress, a new session's graph selection, or memory extraction jobs, commit through turn extensions inside the host's turn transaction. Peer graph turns record their top-level role on the host turn, so usage and transcript queries do not read graph tables.

The owner-scoped schema replaces the earlier single version chain without an upgrade path. The app-server refuses a `state.sqlite` created by an earlier v2 development build and leaves it unchanged; move it aside or delete it, then restart. Schema numbers in the notes below describe that earlier development history.

## First Rust slice

On Windows, `serve` shows a Beale notification-area icon with a running-status tooltip and an **Exit** menu action. Exit gracefully stops the HTTP listener and removes the icon. Ctrl+C remains available in the terminal. Other platforms continue to use terminal shutdown.

`beale-core` is a runnable host that assembles the provider, workspace, session, permission, and plugin routes. `beale-storage` owns the host SQLite schema and typed storage operations. `beale-workspaces` owns workspace validation, registry and manifest operations, and workspace routes; `beale-sessions` owns session operations and routes and depends on the workspace store for workspace membership. `beale-tools` owns the four base host execution tools, model-readable temporary files, and UTF-8 paging for client tool details. `cargo run -p beale-core -- serve` binds `127.0.0.1:43831` by default and serves `GET /v1/health` as `application/x-protobuf`. Set `BEALE_V2_APP_SERVER_ADDR` to another loopback IP and nonzero port when needed; non-loopback bindings are rejected. The desktop uses the same address and validates the service name and protocol version. The v1.59 contract includes authenticated local provider operations, workspace reads and edits, session and Quick Chat turns, archive listing and restoration, permission rule reads, edits, and creation, plugin listing, installation, uninstallation, manifest reads, and workspace scope updates, a framed live session stream, compact tool summaries, positioned reasoning and commentary, separate paged tool detail, a Fleet peer descriptor, and Tracking history. Its protobuf schema is `beale-contracts/proto/beale/v1/host.proto`; the matching Rust `prost` type is kept in source because the bundled Windows `protoc` cannot run in this development environment. The app-server creates a random control token in its private host directory, which the same-device desktop reads for local operations. The host remains bound to loopback; operators can expose it through Tailscale Serve HTTPS. Client-to-host WebSockets are not part of this transport. See the [workspace run instructions](../../README.md) for the two-process flow.

`beale-feature-api` defines the descriptor each native feature crate exports as `FEATURE`: identity, guidance, model tool names and optional static definitions, Auto-Review policy, and whether graph subagents receive the feature. The feature catalog routes, session extension catalog, subagent tool lists, and review policy read these descriptors. `beale-sessions` keeps the turn engine in its own module with a typed turn error; HTTP routes, automations, and peer graph orchestration translate it at their boundaries.

`beale-extender` owns the plugin catalog, installation registry, and MCP server lifecycle. Authenticated `GET /v1/plugins` returns validated package summaries, Skills and MCP Servers counts, recursive scripts/references/assets file counts, and saved install state; `POST /v1/plugins/manifest` returns a selected package's validated `plugin.json` on demand. `POST /v1/plugins/install` and `POST /v1/plugins/uninstall` set or clear that state idempotently by plugin name. The four shipped Agent Plugins packages and user-supplied packages under `~/.beale/v2/plugins/packages/<plugin-name>/` (or `BEALE_V2_HOME/plugins/packages/<plugin-name>/`) can use these routes. The directory name must match `plugin.json` name. SQLite schema 11 adds the install registry and migrates existing host databases in place. Installed MCP servers launch on install or first plugin listing after app-server start. Their paginated `tools/list` results replace bundled tool estimates; bounded launch-time `prompts/list`, `resources/list`, and `resources/templates/list` discovery supplies prompt and resource counts, with unsupported methods contributing zero. A failed server contributes zero tools and does not stop other servers. Stdio and Streamable HTTP are supported, including the older MCP initialization handshake. Uninstall stops active stdio servers. Sessions load installed, in-scope plugin Skills and discovered MCP tool details on demand, then execute selected MCP tools through reviewed `plugin_call`. Git source import is not implemented.

Session summaries include the time of the last saved message. SQLite schema 12 adds this timestamp; existing sessions initialize it from creation time, and subsequent turns update it transactionally.

Goal Mode is a standard `beale-core` harness component in every build. Its implementation lives in `apps/beale-app-server/beale-harness/beale-goals`; the session harness supplies the narrow tool and continuation hooks. A new session opts in through the v1.29 turn request. Max turns and max active-work duration in minutes are optional; zero means unlimited for each. Active duration accumulates completed turn times and excludes time waiting for a user or external change. The host checks configured limits after each completed turn. Only a prompt with Goal Mode selected receives Goal Mode guidance and the `goal_status` tool. It continues until the model records `achieved`, names a concrete external state to wait for, the user stops the turn, an operational failure interrupts it, or a configured limit is reached. A completed turn without `goal_status` continues. Each turn is saved before the next begins. The stream sends intermediate `TURN_COMPLETED` details so the desktop can show progress. Protocol 2.20 adds an authenticated Stop route keyed by a per-stream turn ID; stopping an in-flight provider call saves the turn and pauses the goal. SQLite schema 13 stores goal status and marks generated continuation prompts as internal; schema 14 adds limits and accumulated work time, defaulting existing goals to unlimited. Providers receive internal prompts in context, while clients see only real user messages. Recent turns are supplied to the provider and desktop from a bounded window; earlier turns remain in SQLite. Session execution is serialized per session, leaving other sessions and Quick Chats available during long goals. A new user message resumes a waiting or paused goal unless a configured limit was reached.

Protocol v1.30 adds authenticated feature listing and enablement routes. SQLite schema 15 stores feature state and pauses previously active goals during migration; Goal Mode, Fleet, and Tracking now run as standard harness components. Legacy saved feature toggles and scopes no longer control them. The host owns the feature catalog routes; each native feature supplies its metadata and optional implementation from its own crate. Fleet is available in every host build without a saved feature toggle.

Protocol v1.37 adds Fleet app-server descriptors and authenticator pairing. Authenticated local provisioning returns an `otpauth` URI for a QR code; the 20-byte secret persists in SQLite schema 17. A same-tailnet desktop can submit a current six-digit TOTP code over Tailscale Serve HTTPS to pair, with in-process replay rejection and exponential backoff after failed attempts. The remote host then returns its control token over the verified HTTPS connection. The desktop owns saved remote connections; session routing to remote app servers remains separate. Protocol v1.38 adds authenticated browser inventory and manual add/remove routes. Each host probes conventional browser installation paths and stores manual executables in SQLite schema 18. Browser paths stay on the host. Protocol v1.39 adds authenticated browser setting updates and returns enabled state and workspace scope with inventory; SQLite schema 19 saves those settings. Existing browsers default to enabled for all workspaces. Protocol v1.40 marks the host's preferred browser and adds an authenticated choice update; SQLite schema 20 saves the explicit choice. Until one is saved, the host prefers its OS default browser when present and enabled, then falls back to an enabled browser.

On Windows, the app-server can show this same authenticator QR code from **Show QR Code** in its tray menu. The tray opens a native window and requests the authenticated local provisioning route; closing the window discards the rendered code.

Protocol 2.24 extends the authenticated, Fleet-enabled app-server descriptor with the logical CPU count available to the process, total and available system memory, and total and available space on the volume containing the app-server data directory. The report is sampled per request and returns no host paths. An unavailable individual measurement is zero; the report is omitted if the sampling task fails. Beale Desktop and the app-server must be rebuilt together.

Protocol 2.27 adds the allowed Research Tools list to the authenticated Fleet descriptor so connected peers can inspect each app-server's Local and VM allowances alongside its resources. SQLite schema 48 saves independent allowances per catalog tool. All default off. The app-server offers otool on macOS and jtool2 and dig on macOS and Linux; unavailable tools are omitted from the catalog and allowed-tool list. When Fleet applies to a workspace and at least one tool is allowed, the research prompt lists those tools and their permitted locations. Installation uses existing reviewed execution tools. Rebuild and restart desktop and app-server together. Update any connected desktops before allowing tools added to the catalog because older clients validate descriptors against their own tool IDs.

Protocol v1.41 adds an authenticated, read-only Virtual Machines inventory. On Windows, the host runs the local Hyper-V `Get-VM` query with a fixed command and returns bounded VM IDs, names, states, and generations. Hosts without Hyper-V return an empty list; an installed host that cannot be queried returns an inventory error. VM paths and configuration do not cross the API.

Protocol v1.47 adds graph node model choices and per-role Max Concurrent values to the first session turn and session detail. The optional `beale-graphs` crate defines Simple Orchestra with one main agent and a single Scout, Reviewer, and Prover layer. The main role accepts one model and has a fixed concurrency maximum of 1; subagent limits remain optional. Graphs is disabled by default, and the host accepts the graph only when the feature applies to the chosen workspace. SQLite schema 26 saves the graph configuration with the first turn; existing graph selections retain their graph ID and model choices. When enabled, Simple Orchestra gives the main agent `graph_subagents_spawn`, `graph_subagents_list`, `graph_subagents_inspect`, `graph_subagents_message`, and `graph_subagents_kill`. Spawn returns child IDs immediately, so the parent can keep working and check child status, activity age, live transcripts, tool calls, and results. Each batch starts up to eight role assignments in fresh contexts under the saved per-role concurrency limit. A child can inspect or message siblings within the same top-level agent group; only the parent can stop a child. Saved child transcripts remain inspectable by that top-level parent in later turns. Inspect returns bounded activity pages; live snapshots retain the latest 256 entries and mark truncated text, arguments, and tool output. Subagents use their configured provider and model, the same reviewed base tools, and temporary files for oversized results; they cannot spawn children. Delivered graph messages are saved as transcript-only `graph_subagents_receive` activity with the sender role; it is not a model-callable tool. The host waits for active children before saving the parent turn, retaining their tool calls and results. The parent owns the final response. No Graph leaves the graph ID empty and runs only the main agent.

Protocol v1.44 adds authenticated automation run status alongside listing and cancellation. The first completed session turn with a Repeat preset records a job and its initial run. SQLite schema 23 saves the options needed for later occurrences. The host claims due jobs, runs each occurrence in a new session, and records completion or failure. A stopped host skips old missed occurrences when it resumes. The desktop can skip the next planned occurrence or cancel the series.

Protocol v1.42 adds an authenticated VM settings update and returns enabled state, workspace scope, Can Run, and Can Clone in inventory. SQLite schema 21 saves these per VM ID. Newly detected VMs start enabled for all workspaces, while both access allowances start off. The host accepts settings only for a VM still in its local inventory; these fields do not start or clone a VM.

Protocol v1.31 marks whether each feature provides a system-prompt extension. Goal Mode publishes its guidance file only during active goal turns.

Protocol v1.32 adds an authenticated, on-demand feature-details route for optional features. Live Goal Mode limits and progress are included in the per-turn guidance file.

Protocol v1.33 adds model-facing tool counts to the optional feature catalog. Goal Mode contributes one `goal_status` tool only during active goal turns.

Protocol v1.34 adds the MCP tool count to each Plugin summary. Available bundled cards use a source inventory; installed cards use live server discovery.

Protocol v1.35 adds workspace scope to Plugin and Feature summaries and authenticated `POST /v1/plugins/scope` and `POST /v1/features/scope` updates. Installed Plugins and enabled Features default to All Workspaces. The scope can be any selected subset or No Workspaces; selecting All Workspaces resets it. SQLite schema 16 persists this choice, validates workspace IDs against the registry, and removes deleted workspace IDs without expanding a restricted scope to All Workspaces. Goal Mode is selected per prompt and has no Feature workspace scope. Plugin scope also controls which installed Skills and MCP tools are published to sessions and can be called.

`beale-safety` owns the host-saved Auto-Review and Guardian rule catalog. Before `read`, `write`, `edit`, `bash`, or `webfetch`, the selected review model checks enabled Auto-Review rules. OpenAI subscription reviews use the active research model; other providers use the configured small model. The Guardian review model revisits a completed denial when Guardian rules are enabled. Invalid or unavailable reviews deny the tool call. Each rule's name, instruction, and enabled state can be edited through authenticated `GET` and `PUT /v1/permissions/rules`. Authenticated `POST` creates a rule in either stage with a host-assigned ID, enabled by default. The catalog is limited to 16 rules. Rules are stored in the host SQLite database; schema 10 adds stage and ordering fields for custom rules while preserving earlier rule settings. These model reviews do not provide OS isolation.

`POST /v1/workspaces` accepts a protobuf `CreateWorkspaceRequest` with a name, operator-selected absolute directory, optional guidance, optional typed surfaces, and rules. `GET /v1/workspaces` returns saved workspace summaries; `GET /v1/workspaces/{id}` returns workspace details from the host-owned manifest and guidance file. All require the local control token. The host requires an empty dedicated directory, rejects duplicate surface identities and existing workspace paths, and never adopts existing directory content. A successful create writes schema 7 `workspace.json`, `AGENTS.md`, `RULES.md`, `.beale/`, and the standard research directories, then registers the workspace in the host SQLite database. Existing schema 3 through 6 manifests migrate on read and persist as schema 7 on the next write.

Custom Instructions import validates the model's complete draft before workspace creation. If the draft fails, the host requests a corrected JSON draft up to two times. Surface relationship references must resolve to explicit temporary keys. Each surface records its own scope; a relationship does not authorize its target. Invalid references and duplicate surfaces are rejected.

`GET /v1/workspaces/{id}/campaign`, `/foundation`, `/surfaces`, and `/rules` have separate response types. Campaign currently returns no enabled features. `PUT` on Foundation, Surfaces, and Rules accepts only that section's fields and its expected revision, returns the saved section with its next revision, and rejects stale revisions with `409`. `GET` and `PUT /v1/workspaces/{id}/surfaces/{surface_id}/mapping` and `/threat-model` read and replace separate per-surface records with their own expected revisions. Existing schema-v3 workspaces without revision fields begin at revision 1. The host keeps the workspace directory fixed, allows an empty surface list, and records edits in each surface's lineage. The aggregate `GET /v1/workspaces/{id}` remains available.

Creation writes to an empty operator-selected directory and does not delete it on a filesystem failure. A failed operation can therefore leave a partial directory that must be inspected before retrying; the host will not adopt it as a new workspace.

`beale-providers` owns host-only OpenAI, xAI, Anthropic, Z.ai, OpenRouter, and custom API-provider credentials and text inference. Built-in API-key requests use a saved host key when configured, falling back to the corresponding `OPENAI_API_KEY`, `XAI_API_KEY`, `ANTHROPIC_API_KEY`, `ZAI_API_KEY`, or `OPENROUTER_API_KEY` environment variable. OpenAI subscription requests use the host Codex sign-in and Codex Responses backend; xAI uses device authorization and the Grok Build chat proxy. The xAI proxy requires a client-version header for text turns. The xAI subscription device client ID currently matches the one used by v1; it is isolated in the OAuth module for replacement with a Beale-specific registration. Provider routes centralize endpoint and wire-shape choices so additional adapters can be added without changing the host contract. API-key inference routes stream upstream responses and require a terminal success event. The Anthropic and Z.ai subscription adapters use official CLI turns with structured tool decisions; they currently deliver each step when the CLI completes it. OpenAI subscription model IDs follow the local Codex catalog; other model IDs come from their provider adapters. The host uses a local OpenAI subscription catalog and lists other providers' account-available text models, recommends lead and small choices from that list, and stores selected defaults separately for each provider and sign-in method. OpenAI model display names replace dashes with spaces; model IDs remain unchanged. A default save is checked against the current catalog. A saved choice that disappears from the catalog falls back to an available model. The current subscription recommendations prefer OpenAI GPT-5.6 Sol and GPT-6 Luna, or xAI Grok 4.7 and an available fast variant; actual selections depend on account availability.

Anthropic uses the Messages API with streamed text and tool-use blocks. Z.ai and OpenRouter use chat completions; OpenRouter model IDs keep their provider prefix. Custom providers have host-owned definitions and optional protected keys, use a configured OpenAI-compatible `/chat/completions` endpoint, and retain provider-qualified model IDs in saved sessions. The custom registry and credential operations are authenticated local protobuf routes. OpenAI and xAI retain subscription sign-in. Anthropic subscription turns use the official Claude CLI with its direct tools disabled; Z.ai subscription turns use the official ZCode app-server protocol with no delegated tools. The Rust harness executes requested Beale tools and retains session history; neither adapter copies subscription tokens. ZCode on Windows and macOS needs the installed ZCode bundle and Node on PATH. OpenRouter and custom providers use API keys. Live provider tests require operator credentials and remain opt-in.

Codex owns its sign-in file and renewal. The xAI sign-in command prints a provider URL or device code and saves its OAuth credential under the current user's `.beale/v2` directory (or `BEALE_V2_HOME`). On Unix files are created with mode `0600`; on Windows the host sets a user-only file ACL before replacing a saved record. API keys are read from the host environment and are never written by these commands. `infer` reads the prompt from standard input. Live provider calls require user-provided credentials and have not been exercised by the automated tests.

The CLI is a local provider verification path. Codex account selection and renewal belong to Codex; Beale does not store an OpenAI subscription grant. The app-server has an authenticated local session turn endpoint with completed-turn and tool-call storage in its host database. Remote client authentication and a Tailscale listener remain unimplemented.

The app-server stores source priority per provider in its private database. Subscription is the default when both credentials are configured; an explicit API Key choice is retained across restarts. If only one credential is configured, the desktop uses that source for model settings. The app-server stores the lead provider in the same database. The first provider configured becomes lead, and adding another provider leaves the choice intact. A local client may select another configured provider. Removing the lead provider's last credential reassigns lead to an available provider, or clears it when none remain. If both providers were configured before this setting existed, the app-server uses OpenAI as the initial fallback because their original add order was not recorded.

The OpenAI-only Daybreak Mode setting appears in provider status and accepts Blue or Red through authenticated `POST /v1/providers/openai/daybreak-mode`. Blue is the default; an explicit Red choice is stored in the private host database. Every OpenAI Responses request, including Quick Chat and tool rounds, sends `access_programs.cyber`. The host selects `daybreak_blue` for general-purpose models and `daybreak_red` for known Red cyber models; GPT-6.1 Sol and GPT-6 Astra require Red approval but still send `daybreak_blue`. The Blue-mode model catalog excludes known Red-required models, and a request for one fails before the provider call with a specific error. Unknown models request `daybreak_blue` and may be rejected by the provider if unsupported. The host rejects a response that explicitly selects a different Cyber program. This follows [OpenAI's model-specific Daybreak rules](https://developers.openai.com/api/docs/guides/daybreak). New OpenAI lead defaults prefer GPT-5.6 Sol when available; existing saved choices remain in place.

OpenAI subscription inference reads Codex's host credential for each request and sends Responses requests to the Codex backend with the selected Daybreak program. Codex owns credential renewal. Older Beale OpenAI OAuth records are ignored and left in place; saved API keys remain available. A provider response selecting Standard while Daybreak is requested fails with an explicit program-mismatch error. API-key requests use the same public API with the configured API key.

OpenAI API-key inference uses the public Responses WebSocket with `store: false`. Subscription inference uses Codex's SSE Responses route with `store: false` and complete host-held input for each tool step. For API-key tool loops, the host sends only new items with the previous response ID on the same connection; on a lost connection it replays host-held input. Public API requests enable server-side compaction at 100,000 tokens. Codex subscription requests replay the complete host-held input with encrypted reasoning when available. SQLite schema 24 stores that replay context with each completed session turn. API-key tools retain the `beale` namespace; Codex subscription tools use plain function definitions. The host combines terminal response output with finished output-item events by index so tool calls are retained even when the terminal output array is empty.

Session routes require the local control token. GET /v1/sessions lists unarchived saved sessions, GET /v1/sessions/{id} returns a transcript with compact tool descriptions, POST /v1/sessions/{id}/archive archives a session, and POST /v1/sessions/{id}/restore returns it to workspace lists. GET /v1/archive returns bounded titles, models, workspace IDs, turn counts, and timestamps for archived sessions and Quick Chats. POST /v1/sessions/turns runs a turn through the chosen provider and credential method. GET /v1/sessions/{id}/tools/{tool_id}?offset=N fetches that tool's arguments and up to 8,000 bytes of retained output. The host stores full tool output up to 8 MB per call, bounded reasoning and commentary, and turn duration in SQLite; schema 7 adds session archive timestamps and migrates earlier schemas in place.

For model context, results larger than 8 KB send a UTF-8-safe head/tail preview and the path to a temporary file containing the complete retained output. Main agents and subagents use `read` with line ranges or `bash` to inspect omitted content. The desktop tool-detail route continues to page durable output independently.

Sessions start with four base tools: `read`, `write`, `edit`, and `bash`. Webfetch is an optional single-tool feature in `extensions/features/beale-webfetch`, compiled by the default host build but disabled until enabled in Extensions > Features. When enabled and scoped to the workspace, its `webfetch` tool searches the web or retrieves bounded text and links from HTTP(S) pages without executing JavaScript. Main agents and Graphs subagents share its availability, Auto-Review/Guardian checks, and execution-time scope checks. Host builds can omit it by disabling default Cargo features and leaving `webfetch` off. Enabled, workspace-scoped feature tools are available on the first model step. Installed, scoped plugins with discovered tools enable the generic `plugin_call`.

Each turn publishes an `EXTENSIONS.md` catalog, `features/<id>/FEATURE.md`, and `plugins/<id>/PLUGIN.md` beneath a unique `beale-agent-<uuid>` directory in the operating-system temp directory. Plugin skill files and their scripts, references, and assets retain relative paths beneath `plugins/<id>/skills`; private package configuration and host data are not copied. The system prompt supplies only the catalog path; the catalog contains use cases and instruction paths. Graph subagents receive a separate `subagents/EXTENSIONS.md` listing only their available features. Guidance is read with ordinary file tools. These snapshots and result files survive turn completion for provider-context replay, but may be removed by operating-system temp cleanup.

The agent reads optional workspace `AGENTS.md`, reads the generated `RULES.md` before target operations, and uses enabled Surfaces tools for current scope. `workspace.json` remains the canonical rules store; workspace edits update `RULES.md`, and opening workspace details or starting a turn repairs missing/stale projections without a schema migration. The stock host `SYSTEM.md` is upgraded only when it exactly matches a previous stock default; user-edited prompts are preserved.

Bash uses the user's host privileges with a 120-second default timeout (up to 600 seconds); the app-server does not provide OS isolation. Bash, runbook cells, and Findings verification commands start from an allowlisted environment (shell, locale, proxy, certificate, toolchain, and Windows system variables), so provider API keys, credential-named variables, and `BEALE_*` settings in the app-server environment are not inherited. Set `BEALE_V2_TOOL_ENV` to a comma-separated list of additional variable names to pass through; credential-named entries are ignored. MCP plugin servers keep their environment minus credential-named variables. Each command runs in its own process group or Windows job object: a timeout, oversized output, or stop ends its descendants, while background processes left by a command that exits normally keep running. Before tool output is saved, shown, or returned to a model, the host replaces exact occurrences of the secrets it holds or can read (control token, saved API keys, OAuth and Codex sign-in tokens, and credential-named environment values) with `[redacted host secret]`; encoded or transformed values are not detected. Main agents, peer roles, and graph subagents use one dispatch path for Auto-Review, tool availability, execution, and redaction. A new session is saved after a provider response, or after tool activity if the provider stops before completion; the latter turn records an interruption message. Session history is local to the app-server and bound to a registered workspace.

`POST /v1/quick-chats/turns` accepts an optional chat ID, bounded prompt, and optional selected workspace ID, then returns the saved title and user/assistant transcript. The host selects its configured lead provider, source priority, and lead model for the first turn; later turns keep that selection. Quick Chats use a reserved internal session identity and are archived when first saved, outside workspace session lists. A selected workspace contributes saved guidance, rules, and scope to the system prompt, with no file tools; the host validates the workspace and binds its ID to the chat in SQLite schema 6. Existing no-workspace Quick Chats migrate with an empty binding, and schema 7 archives existing saved Quick Chats. Authenticated GET /v1/quick-chats/{id} reloads a saved chat for desktop restoration; the active chat is hidden from the Archive list until closed.

The v1.13 session contract forwards the selected reasoning effort to OpenAI Responses turns. The v1.12 session contract added positioned reasoning summaries, intermediate assistant text, turn duration, and a live turn stream. `POST /v1/sessions/turns/stream` returns `application/x-beale-protobuf-stream`: each `SessionStreamEvent` is protobuf encoded behind a four-byte big-endian length. It sends provider text and available summary deltas as they arrive, tool start and finish events, then a completed `SessionDetail` or a bounded failure. The prior completed-turn endpoint remains available. Tool arguments and output stay host-only until requested through the detail route. OpenAI Responses requests opt into summaries; xAI Responses summaries are retained when supplied. The xAI subscription chat adapter omits raw reasoning content and currently has no summary field to forward. Raw reasoning text is never sent to clients. SQLite schema 5 stores bounded summaries, intermediate text, and turn durations, migrating existing schema-1 through schema-4 sessions in place.

## System prompt

The app-server creates `~/.beale/v2/SYSTEM.md` on startup if it is missing (or `SYSTEM.md` beneath `BEALE_V2_HOME`). It preserves existing edits and rereads the file at the start of each session turn, so changes apply without a restart. The stock prompt covers the four base tools, temporary result files, workspace `RULES.md` and optional `AGENTS.md`, and reading extension guidance. Runtime sections add the extension catalog path and any enabled memory recall; they do not repeat the base instructions or inline the catalog. Subagents add only their role and task-specific context. Prior unchanged stock prompts upgrade automatically; migration snapshots are never sent to models. Custom edits are preserved. There are no placeholder substitutions. The prompt file is limited to 64 KiB, and the composed prompt to 96 KB.

Subscription usage is available through authenticated GET /v1/providers/usage. The host caches snapshots for five minutes and returns only bounded percentages and reset times. OpenAI's circle and inference read the same Codex sign-in from ~/.codex/auth.json (or CODEX_HOME, APP_SERVER_CODEX_AUTH_FILE, or BEALE_OPENAI_CODEX_AUTH_FILE). xAI's circle uses the host's xAI subscription credential. Unavailable windows are omitted.

Tracking is a standard host component in `apps/beale-app-server/beale-harness/beale-tracking`. Authenticated `GET /v1/tracking` returns at most seven days of observed subscription windows and daily aggregates of Beale research-session model calls. Schema 27 stores subscription samples and per-call main or subagent identifier, role, model, duration, and provider-reported token counts. Samples are collected only when provider usage is checked while the host runs; earlier history is not backfilled. Calls without reported token counts retain duration and are counted as unmeasured for token totals. The route is host-wide and cannot be scoped to individual workspaces. Protocol 2.14 appends optional cache-read tokens, cache-covered input tokens, and cache-measured call counts to each daily aggregate. Cache reads are included in input tokens. The hit-rate denominator includes only calls with cache telemetry; zero measured calls means unknown. These fields use existing schema 33 columns and require no migration. Current desktop clients require a rebuilt/restarted 2.17 host.

The Surfaces feature is compiled into the default host build but disabled in saved feature state until enabled for a workspace. It supplies six model tools: `surface_query`, `surface_read`, `surface_save`, `surface_mapping_edit`, `surface_promote_element`, and `surface_threat_model_edit`. `surface_read` selects the record, mapping, or threat model; `surface_save` explicitly creates or revises a surface. Mapping and threat-model reads are paged. Each mapping is stored independently in `.beale/surface-mappings/`; each threat model is stored in `.beale/surface-threat-models/`, with its own revision and reviewed mapping revision. Threat scenarios are hypotheses anchored to local element or flow IDs; new references must resolve, while older references remain readable and are flagged when mapping edits make them stale. Dismissals require a reason. Promotion creates a separate surface and an anchored relationship while retaining the source element. Mapping flows cannot reference another surface. When disabled, sessions and Quick Chat omit surface records from model context and sessions omit these tools. Workspace rules remain available for general authorization boundaries. Every surface requires a definition with type, locator, and scope; a workspace without an in-scope surface must record at least one Rule. Each surface has only `id`, `definition`, `relationships`, and `lineage` at the top level. Definitions, relationships, mapping entries, and threat scenarios can cite typed `SurfaceEvidence` references (`kind`, `reference`, and optional `note`). Schema 7 manifests migrate old parent IDs to explicit `contains` relationships and legacy narrative fields into `description`; progress fields are discarded. Deleted surfaces retain their lineage, mapping, and threat model. The threat-model route advances the protocol to 2.3.

Findings is an optional feature, disabled by default. Each finding has a summary, zero or more surface IDs, optional `FindingRootCause` and `FindingAttackPath` objects, and optional remediation text. Root cause has a summary and typed evidence references. Attack path records assumptions, typed evidence, limitations, preconditions, likelihood, impact, steps, and nested reachability details (summary, attacker role, entrypoint, source, and sink). Its `FindingState` contains a required Candidate object and optional Validated, Screened, Reported, and Rejected objects, each accepting typed evidence references. Its displayed status is derived from completed objects and predecessor revisions. Seven on-demand `findings_*` tools query, read, create, update finding or state details, complete a state, reject a finding, and verify a proof. Validation records a method name, description, result description, limitations, and typed counter-evidence; completion requires the first three plus a host-checked successful `read`, `bash`, or verified `findings_verify` tool-call reference from the same workspace, made after the Candidate was recorded, but no PoC. In Research Pipelines the cited call must come from the Validation role or its subagents. Completion stores a SHA-256 digest of each cited result. Saved tool calls record their completion time, which the binding compares with the Candidate's creation time. `findings_verify` reruns a declared command twice in fresh workspace processes after Auto-Review and records whether a host-evaluated oracle held on every run: `exit_code`, `exit_nonzero`, `stdout_contains`, `stderr_contains`, or `output_contains`. Oracle text may not appear in the command. The verification (command, oracle, per-run exit codes and output digests, requesting role, and tool call) is host-owned and cannot be patched; summaries report `verified`. Verification shows that a command's result reproduces, not that the command is a meaningful proof, and is not required for validation. An empty limitations or counter-evidence list is allowed. Screening records validation-quality, known-issue/accepted-risk, and scope/reportability checks, plus 0–100 integer impact and reachability scores. Completion requires both scores, a root-cause summary, and nonempty reachability summary, attacker role, entrypoint, source, and sink inside the attack path. The Reported object holds the triage-facing PoC and report reference; the tool refuses to draft it until screening is complete. Authenticated `POST /v1/findings/query` and `/get` provide client reads. Query returns total and next offset for pagination; get returns the current record by default and one revision when `history_offset` is supplied. App-server schema 42 migrates schema-41 findings, schema 43 stores revisions separately from current records, and protocol 2.17 carries the current client contract. Older findings without newer optional fields remain readable. When enabled for a workspace, Findings has desktop Ledger and Plot views. The ledger has Candidate, Validated, Screened, and Reported lanes; the plot places recorded impact scores vertically and reachability scores horizontally. Rejected and unrated findings stay outside the plot and remain accessible. Draft screening ratings may be plotted while the finding remains Validated. Both views refresh automatically while open and share read-only details.
