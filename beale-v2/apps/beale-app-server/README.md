Swarm scheduling is detached from requests. The first submission for a scan starts one scheduler task, which owns the scan's session lock until no agent is running or eligible. Leader publication-storage reservations have a placement owner from admission through durable execution binding. ## Storage

The host database is `state.sqlite` beneath `BEALE_V2_HOME` or `~/.beale/v2`. Each schema owner records its own version in `schema_versions`. The `host` owner (in `beale-storage`) holds workspaces, sessions, turns, tool calls, reasoning and commentary, subagent transcripts, model usage, provider context, Quick Chat bindings, provider settings, permission rules, plugin installs, feature and extension scope state, and automations. Each native feature owns its tables and applies its migrations under its feature ID when the host starts: Findings, Runbooks, Fleet, Tracking, Goal Mode, Memories (the extraction queue; extracted memories stay in `memories.sqlite`), and the independently initialized Swarms repository (snapshotted definitions, agents, assignments, and workflow handoffs). Optional feature tables are absent when that feature is omitted from the build; Goal Mode, Fleet, and Tracking tables remain available in every build. Feature rows that must be saved atomically with a turn, such as Goal Mode progress, memory extraction jobs, commit through turn extensions inside the host's turn transaction. Swarm state is initialized on demand; retired Graph sessions are rejected without conversion or deletion.

The owner-scoped schema replaces the earlier single version chain without an upgrade path. The app-server refuses a `state.sqlite` created by an earlier v2 development build and leaves it unchanged; move it aside or delete it, then restart. Schema numbers in the notes below describe that earlier development history.

Stage 4 adds the version-1 `swarm-files` storage schema and path-free JSON manifest, artifact, and environment contracts. A new local Swarm seals one verified initial workspace snapshot before model execution. Leaders keep the original workspace; each deputy and worker gets its own writable directory, reused on related resume. Native read/write/edit tools, command execution, runbook execution, and finding verification use that assigned directory. The file-tool exception permits only the assigned directory inside host storage; sibling environments and canonical databases remain blocked by native file tools. This does not isolate arbitrary same-user shell commands.

Retained roots cannot be replaced with directory links: reopen and native dispatch reject aliases, as do publication and materialization paths. Checkpoint replay and resume verify retained context bytes and ownership. Transferred manifest entry order does not affect materialization. Snapshot exclusions cover the entire configured host-data boundary, including explicit external mounts, and repository history checks include merge-only paths.

Local artifact attachments use `file:relative/path` in finding artifact evidence or handoff `artifact_refs`. The host publishes bytes and provenance before committing the canonical mutation. Provenance includes the producing attempt and generation, the real child assignment when applicable, and an explicit absent assignment for coordinators. Managed references retain integrity and workspace checks even when an operator or ordinary session later edits the record. Existing artifact IDs must resolve to accepted bytes in the same workspace. `swarm_materialize_artifact` takes `{artifact, destination}` and creates a separate file without overwriting existing edits. Acceptance is storage acknowledgement, not vulnerability verification. Transfers use bounded chunks, fixed content identities, verified seals, and persistent offsets; checkpoint and publication failures preserve the prior acknowledgement and pending outputs.

The snapshot adapter excludes host database names, credential/runtime directories and files, and Git configuration. Git inputs require a local Git executable: history is bundled into snapshot-owned objects, linked worktrees become self-contained, and executable index metadata is preserved. History containing excluded paths, staged/unmerged indexes, submodules, unsupported link types, escaping or relocated link targets, case collisions, unrepresentable permissions, and unsupported destination names fail explicitly. Native Windows materialization rejects symlinks and executable artifacts without a representable executable bit; a repository index can preserve known executable metadata. Native Linux tests cover symlink and executable semantics. Unix materialization reads back permission bits before publication and rejects mounts that silently ignore the requested permissions. Capture verifies two passes with at most three attempts; a changing source must be quiesced. Git platform path-length failures remain explicit errors.

Host storage APIs accept explicitly mounted external inputs; automatic local scan capture uses only its workspace root and never discovers external roots implicitly. Environment descriptors retain workspace components, checkpoint references, publication dependencies, and local restore compatibility. Directory reopen preserves edits and rejects missing/incompatible retained storage. File adapters verify bytes and metadata; Fleet owns retained-environment cleanup, Docker lifecycle, and cross-host restore. Worker routing and recovery are described above. Earlier development scans without a sealed workspace snapshot are not silently recaptured.

Removing the lead provider's last credential reassigns lead to an available provider, or clears it when none remain. If both providers were configured before this setting existed, the app-server uses OpenAI as the initial fallback because their original add order was not recorded.

The OpenAI-only Daybreak Mode setting appears in provider status and accepts Blue or Red through authenticated `POST /v1/providers/openai/daybreak-mode`. Blue is the default; an explicit Red choice is stored in the private host database. Every OpenAI Responses request, including Quick Chat and tool rounds, sends `access_programs.cyber`. The host selects `daybreak_blue` for general-purpose models and `daybreak_red` for known Red cyber models; GPT-6.1 Sol and GPT-6 Astra require Red approval but still send `daybreak_blue`. The Blue-mode model catalog excludes known Red-required models, and a request for one fails before the provider call with a specific error. Unknown models request `daybreak_blue` and may be rejected by the provider if unsupported. The host rejects a response that explicitly selects a different Cyber program. This follows [OpenAI's model-specific Daybreak rules](https://developers.openai.com/api/docs/guides/daybreak). New OpenAI lead defaults prefer GPT-5.6 Sol when available; existing saved choices remain in place.

OpenAI subscription inference reads Codex's host credential for each request and sends Responses requests to the Codex backend with the selected Daybreak program. Codex owns credential renewal. Older Beale OpenAI OAuth records are ignored and left in place; saved API keys remain available. A provider response selecting Standard while Daybreak is requested fails with an explicit program-mismatch error. API-key requests use the same public API with the configured API key.

OpenAI API-key inference uses the public Responses WebSocket with `store: false`. Subscription inference uses Codex's SSE Responses route with `store: false` and complete host-held input for each tool step. For API-key tool loops, the host sends only new items with the previous response ID on the same connection; on a lost connection it replays host-held input. Public API requests enable server-side compaction at 100,000 tokens. Codex subscription requests replay the complete host-held input with encrypted reasoning when available. SQLite schema 24 stores that replay context with each completed session turn. API-key tools retain the `beale` namespace; Codex subscription tools use plain function definitions. The host combines terminal response output with finished output-item events by index so tool calls are retained even when the terminal output array is empty.

Session routes require the local control token. GET /v1/sessions lists unarchived saved sessions, GET /v1/sessions/{id} returns a transcript with compact tool descriptions, POST /v1/sessions/{id}/archive archives a session, and POST /v1/sessions/{id}/restore returns it to workspace lists. GET /v1/archive returns bounded titles, models, workspace IDs, turn counts, and timestamps for archived sessions and Quick Chats. POST /v1/sessions/turns runs a turn through the chosen provider and credential method. GET /v1/sessions/{id}/tools/{tool_id}?offset=N fetches that tool's arguments and up to 8,000 bytes of retained output. The host stores full tool output up to 8 MB per call, bounded reasoning and commentary, and turn duration in SQLite; schema 7 adds session archive timestamps and migrates earlier schemas in place.

For model context, results larger than 8 KB send a UTF-8-safe head/tail preview and the path to a temporary file containing the complete retained output. Main agents and subagents use `read` with line ranges or the host command tool to inspect omitted content. The desktop tool-detail route continues to page durable output independently.

Sessions start with four base tools: `read`, `write`, `edit`, and `powershell` on Windows (`bash` elsewhere). Protocol 2.29 updates the Windows tool name and desktop handling. The Windows tool launches Windows PowerShell without a profile or interactive prompts from the workspace. Webfetch is an optional single-tool feature in `extensions/features/beale-webfetch`, compiled by the default host build but disabled until enabled in Extensions > Features. When enabled and scoped to the workspace, its `webfetch` tool searches the web or retrieves bounded text and links from HTTP(S) pages without executing JavaScript. Local sessions apply its availability, Auto-Review/Guardian checks, and execution-time scope checks. Host builds can omit it by disabling default Cargo features and leaving `webfetch` off. Enabled, workspace-scoped feature tools are available on the first model step. Installed, scoped plugins with discovered tools enable the generic `plugin_call`.

Each turn publishes an `EXTENSIONS.md` catalog, `features/<id>/FEATURE.md`, and `plugins/<id>/PLUGIN.md` beneath a unique `beale-agent-<uuid>` directory in the operating-system temp directory. Plugin skill files and their scripts, references, and assets retain relative paths beneath `plugins/<id>/skills`; private package configuration and host data are not copied. The system prompt supplies only the catalog path; the catalog contains use cases and instruction paths. Guidance is read with ordinary file tools. These snapshots and result files survive turn completion for provider-context replay, but may be removed by operating-system temp cleanup.

The agent reads optional workspace `AGENTS.md`, reads the generated `RULES.md` before target operations, and uses enabled Surfaces tools for current scope. `workspace.json` remains the canonical rules store; workspace edits update `RULES.md`, and opening workspace details or starting a turn repairs missing/stale projections without a schema migration. The stock host `SYSTEM.md` is upgraded only when it exactly matches a previous stock default; user-edited prompts are preserved.

The host command tool uses the user's host privileges with a 120-second default timeout (up to 600 seconds); the app-server does not provide OS isolation. The host command tool, runbook cells, and Findings verification commands start from an allowlisted environment (shell, locale, proxy, certificate, toolchain, and Windows system variables), so provider API keys, credential-named variables, and `BEALE_*` settings in the app-server environment are not inherited. Set `BEALE_V2_TOOL_ENV` to a comma-separated list of additional variable names to pass through; credential-named entries are ignored. MCP plugin servers keep their environment minus credential-named variables. Each command runs in its own process group or Windows job object: a timeout, oversized output, or stop ends its descendants, while background processes left by a command that exits normally keep running. Before tool output is saved, shown, or returned to a model, the host replaces exact occurrences of the secrets it holds or can read (control token, saved API keys, OAuth and Codex sign-in tokens, and credential-named environment values) with `[redacted host secret]`; encoded or transformed values are not detected. Local sessions use one dispatch path for Auto-Review, tool availability, execution, and redaction. A new session is saved after a provider response, or after tool activity if the provider stops before completion; the latter turn records an interruption message. Session history is local to the app-server and bound to a registered workspace.

A selected workspace contributes saved guidance, rules, and scope to the system prompt, with no file tools; the host validates the workspace and binds its ID to the chat in SQLite schema 6. Existing no-workspace Quick Chats migrate with an empty binding, and schema 7 archives existing saved Quick Chats. ## System prompt

The app-server creates `~/.beale/v2/SYSTEM.md` on startup if it is missing (or `SYSTEM.md` beneath `BEALE_V2_HOME`). It preserves existing edits and rereads the file at the start of each session turn, so changes apply without a restart. The stock prompt covers the four base tools, temporary result files, workspace `RULES.md` and optional `AGENTS.md`, and reading extension guidance. Runtime sections add the extension catalog path and any enabled memory recall; they do not repeat the base instructions or inline the catalog. Subagents add only their role and task-specific context. Prior unchanged stock prompts upgrade automatically; migration snapshots are never sent to models. Custom edits are preserved. There are no placeholder substitutions. The prompt file is limited to 64 KiB, and the composed prompt to 96 KB.

Subscription usage is available through authenticated GET /v1/providers/usage. The host caches snapshots for five minutes and returns only bounded percentages and reset times. OpenAI's circle and inference read the same Codex sign-in from ~/.codex/auth.json (or CODEX_HOME, APP_SERVER_CODEX_AUTH_FILE, or BEALE_OPENAI_CODEX_AUTH_FILE). xAI's circle uses the host's xAI subscription credential. Unavailable windows are omitted.

Tracking is a standard host component in `apps/beale-app-server/beale-harness/beale-tracking`. Authenticated `GET /v1/tracking` returns at most seven days of observed subscription windows and daily aggregates of Beale research-session model calls. Schema 27 stores subscription samples and per-call main or subagent identifier, role, model, duration, and provider-reported token counts. Samples are collected only when provider usage is checked while the host runs; earlier history is not backfilled. Calls without reported token counts retain duration and are counted as unmeasured for token totals. The route is host-wide and cannot be scoped to individual workspaces. Protocol 2.14 appends optional cache-read tokens, cache-covered input tokens, and cache-measured call counts to each daily aggregate. Cache reads are included in input tokens. The hit-rate denominator includes only calls with cache telemetry; zero measured calls means unknown. These fields use existing schema 33 columns and require no migration. Current desktop clients require a rebuilt/restarted 2.17 host.

The Surfaces feature is compiled into the default host build but disabled in saved feature state until enabled for a workspace. It supplies four model tools: `surface_query`, `surface_read`, `surface_save`, and `surface_threat_model_edit`. `surface_read` selects the surface record or its threat scenarios; `surface_save` creates or revises a surface. Children have exactly one parent through a `contains` relationship; cycles and multiple parents are rejected. Threat scenarios are hypotheses attached to a surface, and dismissals require a reason. When disabled, sessions and Quick Chat omit surface records from model context and sessions omit these tools. Workspace rules remain available for general authorization boundaries. Every surface requires a definition with type, locator, and scope; a workspace without an in-scope surface must record at least one Rule. Definitions, relationships, and threat scenarios can cite typed `SurfaceEvidence` references (`kind`, `reference`, and optional `note`). Schema 7 manifests migrate old parent IDs to explicit `contains` relationships and legacy narrative fields into `description`; progress fields are discarded. Deleted surfaces retain their lineage and threat model.

Findings is an optional feature, disabled by default. Each finding has a summary, zero or more surface IDs, optional `FindingRootCause` and `FindingAttackPath` objects, and optional remediation text. Root cause has a summary and typed evidence references. Attack path records assumptions, typed evidence, limitations, preconditions, likelihood, impact, steps, and nested reachability details (summary, attacker role, entrypoint, source, and sink). Its `FindingState` contains a required Candidate object and optional Validated, Screened, Reported, and Rejected objects, each accepting typed evidence references. Its displayed status is derived from completed objects and predecessor revisions. Seven on-demand `findings_*` tools query, read, create, update finding or state details, complete a state, reject a finding, and verify a proof. Validation records a method name, description, result description, limitations, and typed counter-evidence; completion requires the first three plus a host-checked successful `read`, host command tool (`powershell` on Windows or `bash` elsewhere), or verified `findings_verify` tool-call reference from the same workspace, made after the Candidate was recorded, but no PoC. In Research Pipelines the cited call must come from the Validation role or its subagents. Completion stores a SHA-256 digest of each cited result. Saved tool calls record their completion time, which the binding compares with the Candidate's creation time. `findings_verify` reruns a declared command twice in fresh workspace processes after Auto-Review and records whether a host-evaluated oracle held on every run: `exit_code`, `exit_nonzero`, `stdout_contains`, `stderr_contains`, or `output_contains`. Oracle text may not appear in the command. The verification (command, oracle, per-run exit codes and output digests, requesting role, and tool call) is host-owned and cannot be patched; summaries report `verified`. Verification shows that a command's result reproduces, not that the command is a meaningful proof, and is not required for validation. An empty limitations or counter-evidence list is allowed. Screening records validation-quality, known-issue/accepted-risk, and scope/reportability checks, plus 0–100 integer impact and reachability scores. Completion requires both scores, a root-cause summary, and nonempty reachability summary, attacker role, entrypoint, source, and sink inside the attack path. The Reported object holds the triage-facing PoC and report reference; the tool refuses to draft it until screening is complete. Authenticated `POST /v1/findings/query` and `/get` provide client reads. Query returns total and next offset for pagination; get returns the current record by default and one revision when `history_offset` is supplied. App-server schema 42 migrates schema-41 findings, schema 43 stores revisions separately from current records, and protocol 2.17 introduced the initial Findings client contract. Older findings without newer optional fields remain readable. When enabled for a workspace, Findings has desktop Ledger and Plot views. The ledger has Candidate, Validated, Screened, and Reported lanes; the plot places recorded impact scores vertically and reachability scores horizontally. Rejected and unrated findings stay outside the plot and remain accessible. Draft screening ratings may be plotted while the finding remains Validated. Both views refresh automatically while open and share read-only details.

Protocol 2.31 adds authenticated `POST /v1/findings/create` for a workspace ID, title, summary, and Candidate hypothesis from Beale Desktop. The Findings feature and workspace scope must be enabled. The app-server validates and stores the Candidate through the same path as the Findings tool, attributing its first revision to the desktop operator. Update connected desktops and app-servers together.

Protocol 2.32 adds optional workspace logos to workspace summaries and foundation updates. The wire thumbnail is empty or exactly 64 × 64 straight-alpha sRGB RGBA pixels. An omitted update preserves the saved logo; a present empty update removes it. The host validates the buffer before saving it as optional `logoRgba` in `workspace.json`, under the existing foundation revision. Older manifests default to no logo without a migration. Update connected desktops and app-servers together.

# Swarms (protocol 2.50)

`swarm_message_parent` handoffs are drafts: the agent supplies `to_profile`, task, scope, evidence, and a typed payload. The host fills in the envelope ID (derived from the tool operation, so replays match), source, parent, destination profile revision, and the saved route for the source deputy, destination, and payload kind. `route_id` is needed only when several saved routes match. The reply includes `handoff_id`. Drafts that name host identity fields are rejected as invalid arguments.

Stop and exhausted leader recovery no longer end a scan permanently. An operator follow-up resumes the leader with its saved conversation once every leader execution has stopped; its descendants stay stopped until the leader resumes them with `swarm_message_subagent`, which also resumes a stopped child after its execution stops. A follow-up that cannot be delivered leaves an ended scan, its end time, and its retention deadlines unchanged.

Leaders keep their coordination tools (list, spawn, message, stop, handoff) without model review; their research calls, including artifact materialization, remain under the coordinator-only rule. Local agents receive typed rejection feedback (`invalid_arguments`, `not_found`, `conflict`, `rejected`) for Swarm and artifact requests, matching assigned workers. An unknown or foreign artifact ID is reported to an assigned worker as a tool error instead of stopping it.

Worker tool output is redacted with the leader's host-secret redactor before it is sent to a provider, and stored worker tool-outcome events are redacted the same way. A worker command, verification run, or Runbook cell that reaches its time or output limit is ended first and reported as a failed result; other collection failures still stop the worker with an uncertain outcome. On Linux each worker command runs in its own process group when the worker runs under the subreaper supervisor (which sets `BEALE_WORKER_SUPERVISED` for its worker) or in a container, because that supervisor or the container stop still proves that every descendant ended. Any other worker, including macOS workers, keeps commands in the worker's group so group termination covers them, and a limit ends only the direct process.

Snapshot chunk reads hash only the blob being served, once when its first chunk is read; receivers verify every object against its manifest digest. Capture and private-copy materialization copy and hash without holding the host database lock. Rebuild Desktop and participating app-servers and workers together for protocol 2.50.

# Swarms (protocol 2.49)

The `swarm-local-workers` schema 3 adds a coordinator-attempt transcript binding. Normal completion saves this binding with the transcript transaction. Lost-owner recovery appends an interruption notice and the claimed operator text to an existing or new session only when that attempt has no committed turn. Repeated recovery preserves the original answer, user text and full model input without duplication. Recovery transcript writes, the binding, hierarchy stop and fencing commit together; storage failures leave the recovery pending. Checkpoint exhaustion may stop execution before its transcript is saved; coordinator completion now preserves the transcript or leaves recovery pending. Background maintenance repairs stopped attempts and finalizes terminal leader turns in the same transaction as transcript repair and recovery completion. Successful completion uses the same terminal-state check as the supervisor: the leader is completed, all executions are stopped, and no assignments remain queued or assigned. A failed scan-end write leaves coordinator recovery pending even when the answer and checkpoint are already saved; owner loss at that boundary preserves the real answer and finishes retention without re-inference. Finalization uses the canonical scan-end operation: it starts retention, revokes worker authority, and preserves Keep, active-use, publication and unconfirmed-termination protections. Historical attempts cannot end a newer leader generation, and completed recovery replay cannot re-end a reopened scan. Earlier development in-flight executions are unsupported across rebuilds.

Host schema 2 stores full Swarm model input separately from user-facing transcript text. Operator messages remain visible and unchanged when mixed with recovery deliveries or custody notices; reopening storage and resuming inference preserve both representations. Existing transcript rows survive the additive nullable-column migration. The wire protocol is unchanged; rebuild participating hosts/workers, and do not reuse unsupported earlier development in-flight turn formats.

The host lists validated custom definitions from `swarm-templates/`. New Swarm configuration snapshots include topology, profile instructions, and the leader-only coordinator rule. Handoffs have typed payloads, parent routes, revision checks, and content-bound retry acknowledgements. The local supervisor runs the saved hierarchy through the existing session engine. Only direct children can be controlled; leaders can inspect all descendants. Leader review uses the immutable scan rule even when global rules or new Swarms are disabled, and carries it through Guardian review. Local recovery stops after three failed attempts; a broken leader stops the tree, while a broken deputy reports to its parent.

The sequential pipeline, sibling messaging, Graph compatibility reader, and legacy-only specialist profiles are removed. Protocol timer tags are reserved. Existing incompatible development state is not rewritten or silently downgraded. See `extensions/features/beale-swarms/README.md` for bundled structures, custom definitions, and tested boundaries.

Local transcript and supervisor checkpoint failures retry the same atomic write up to three times without new inference or tool dispatch. Exhaustion blocks the branch (or stops a broken leader) and retains accepted work. Retryable provider failures keep the client stream open until the supervisor finishes. Parent mailboxes deliver complete typed handoffs; the first child turn includes its assignment alongside queued follow-ups. Completion summaries are truncated at UTF-8 byte boundaries within the mailbox limit, and large inbox batches leave excess messages unread for a later turn.

After tool activity, local provider recovery retries the existing exchange up to three times. Repeated provider call IDs reuse the recorded result when their tool name and canonical arguments match; changed content is rejected. Exhaustion saves partial activity and blocks only the affected branch (or stops a broken leader), without starting another model turn that repeats accepted work. Host lifecycle notices can exceed the ordinary mailbox admission limit to commit completion, cancellation, and recovery; the shared inbox cursor still acknowledges them once. Worker prompts include their immediate parent identity and the saved deputy-stage instructions on execution and resume.

The leader coordinates on the trusted host. Native subagents use private workspace copies without OS isolation; selected Docker destinations run through Fleet admission and supervised worker execution. Managed tools finish or confirm termination before release, checkpoint, or reuse. A scan with selected Fleet destinations never silently executes its subagents locally. Account pacing applies across research and supporting provider calls; admission and pacing remain best-effort controls.

## Docker worker preparation (Stage 6)

Fleet accepts versioned image-name configurations through authenticated `GET/POST /v1/fleet/container-configurations`. Each record selects a Linux architecture and optional environment, user, startup mode, and command override. `worker_idle` starts the injected worker as PID 1 for base OS images. `image_default` preserves the original entrypoint and command unless an explicit command override is supplied. Images whose entrypoint exits, user cannot write the required storage, or runtime cannot execute remain unavailable. Configuration revisions are immutable for retained instances.

The owning host uses its Docker CLI, daemon context, and registry authentication to pull and pin the image's content-addressed ID. `BEALE_DOCKER_CLI` optionally selects that CLI. `BEALE_CONTAINER_RUNTIME` selects a host-local versioned bundle containing a static Linux worker, static Bash, its copyright file, and checksums. Bundle validation rejects dynamic dependencies, architecture mismatches, incompatible protocol versions, and changed bytes. Nothing is installed through the guest's package manager. Build the worker with `cargo build -p beale-core --all-features --release --target x86_64-unknown-linux-musl` (or the matching Arm64 musl target), using an appropriate musl linker. Package the resulting binary with `scripts/package-container-runtime.py --worker <binary> --bash <static-bash> --bash-license <copyright-file> --architecture amd64 --output <new-bundle-directory>`. Packaging requires Python 3 on the build host; the guest requires neither Python nor a preinstalled shell. No binary bundle is committed to this repository.

`DockerEnvironments::prepare` is the host preparation boundary for a reserved instance ID. It records creation intent before mutating Docker, labels its resources, injects and probes the runtime, and retains the stopped container and private named volume. One logical agent owns each instance across attempts. Existing instances are never recreated when retained storage is missing. Interrupted preparation is stopped by background recovery; partial state is retained for inspection. The harness's destination router and restart recovery share the Docker backend. Stage 7 admits selected-scan work, automatically prepares reserved instances, verifies cross-host reconstruction, and cleans eligible retained private state. Saving a configuration alone does not launch research.

Before research, the Linux guest receives the sealed initial snapshot through the scoped worker gateway, verifies filesystem metadata in the guest, and round-trips a small readiness artifact through central publication storage. Git repository snapshots require Git in the selected image; file-only snapshots do not. Later attempts verify the retained snapshot receipt and preserve private edits, installed files outside the workspace, and the original container ID. Worker bootstrap credentials travel on stdin; provider credentials and the host database are not mounted. Readiness failures report bounded runtime, snapshot, retained-storage, or artifact-transfer reasons. The injected runtime directory is prepended to the guest's effective `PATH`, preserving image defaults and explicit environment overrides.

Container research commands use non-login Bash so image login profiles cannot replace that configured path. Host and native-worker shell behavior is unchanged.

Inside a container, loopback is the container itself, so a loopback leader origin is given to the worker as `http://host.docker.internal:<port>`. Docker Desktop resolves that name and forwards it to the host's loopback listener. On a native Linux engine, containers are created with `host.docker.internal` mapped to the default bridge gateway, and the app-server also listens on that gateway at its own port, serving only the scoped worker route; the host control API stays on loopback. The listener starts when Docker becomes available. Rootless engines and custom bridge networks are not configured automatically; set `BEALE_FLEET_LEADER_ORIGIN` to an origin the containers can reach. A paired Fleet HTTPS origin is passed to workers unchanged.

The `fleet-docker` schema version 3 retains the preparation journal introduced in version 2 and adds a monotonic readiness revision. Successful preflight retries restore `Ready` and clear the earlier failure reason. Observations are bound to the configuration, instance, and attempt; late results cannot overwrite newer observations, preparations, or configuration revisions. A failed current readiness write prevents research startup and remains retryable. Restart maintenance resolves interrupted pulls and retries failed final readiness writes without overwriting newer configuration/preparation results. Preparation recovery reloads candidates under the instance lock. Destination restart recovery retains its bounded stop/inspection task and ownership across short maintenance or HTTP polls; replacement stays fenced until termination is durably confirmed.

Retained-instance inspection, startup, runtime-probe, and workspace-preflight failures use the same guarded readiness update. A current preflight failure records `Unavailable` with its bounded reason before returning; termination recovery preserves that reason until successful preflight clears it. Readiness failure does not prove termination or permit replacement.

The default `worker_idle` PID 1 reaps exited orphan children in bounded batches on child signals and periodic sweeps, while leaving live children running. Shutdown signals retain priority, and the host still confirms whole-container termination before reuse. Images using their own entrypoint retain responsibility for their init behavior.

Cancellation and lease expiry stop the entire container, including processes outside the worker's process group. Only a fresh Docker observation of the owned stopped container and volume proves termination. A daemon outage retains unconfirmed ownership and blocks replacement. Short maintenance polls retain an in-progress stop operation rather than continually canceling it. Cleanup checks the exact instance, host labels, pinned image, and workspace volume before removing resources.

The opt-in `docker_acceptance` tests use synthetic leader/provider servers and an explicit static runtime bundle. Set `BEALE_CONTAINER_RUNTIME` and optionally `BEALE_DOCKER_CLI`, then run `cargo test -p beale-sessions --all-features docker_acceptance -- --ignored --nocapture`. Containers reach the fixture's loopback-addressed leader through the same `host.docker.internal` path as production; no fixture host mapping is installed. AMD64 is the exercised native architecture; Arm64 runtime/image mismatches are rejected, and native Arm64 execution requires a matching test host and bundle.


## Provider accounting and pacing (Stage 8)

Protocol 2.43 adds `SubmitSessionTurnRequest.swarm_pacing` and `SessionDetail.pacing_warnings`. Targets are saved with the scan and use an opaque account-budget group, an interval in seconds, and one unit: `subscription` (basis points of a named full allowance window), `currency` (ISO currency micros), or `credits` (credit micros). For example, 100 basis points means one percentage point of the full allowance. Targets cannot be changed by resuming an existing scan. Desktop exposes these controls in New Scan.

The authenticated JSON endpoint `POST /v1/provider-accounting` accepts the typed requests in `beale-contracts::pacing`. `resolve` returns host grouping metadata; `bind` explicitly selects a group, authority, generation, and registered participants for a provider/authentication route. Custom provider routes include their configured provider ID. Reliable Codex account identity is host-only; credential refresh retains its group. Other unresolved identities use a visibly limited local group until explicitly grouped. Neither credentials nor upstream account identifiers enter worker prompts or this protocol.

`price` configures model prices on each inference leader, in currency/credit micros per million input, output, and cached input tokens. These produce **estimated** charges. Missing pricing or usage remains **unknown**. Existing Codex and xAI allowance probes feed named-window observations; absent measurements, stale windows, authority failures, and uncertain charges produce durable session warnings. These warnings and accounting continue with Desktop closed.

The authority admits research and supporting inference, including auto-review and attributable memory extraction. Each scan keeps its target; the shared group uses the largest active scan rate as a conservative aggregate ceiling, rather than multiplying that ceiling by the number of scans. Waiting research and supporting calls alternate when eligible. Before a usable cost sample exists, the reservation heuristic is one sixtieth of the target per call, rounded up to one unit. Known costs reconcile account debt at the saved aggregate rate and scan debt at the scan rate, including shared-account usage from scans without their own target; unknown charges retain uncertainty. This is best-effort pacing, never a guaranteed spending cap or precise attribution of unrelated account activity.

Admission precedes provider dispatch and response timeouts. Every physical attempt dispatched by Beale, including transport retries, gets a distinct durable identity. Provider CLIs can hide their own upstream retries and usage; those integrations count host invocations, retain unknown charges, and warn about the measurement limit. Lost results retain charges; repeated usage delivery does not add cost. Worker requests that may wait for inference admission use independent heartbeat/lease supervision instead of a transport deadline. Cancellation remains active while waiting, and publication/recovery do not acquire inference admission. Review waits precede shared mutation locks.

The version-1 `provider-accounting` schema retains group bindings, scheduler debt, reservations, usage outboxes, acknowledged allocations, prices, observations, and warnings. Streamed usage is persisted before response completion; interrupted responses retain known token counts with uncertain charge status. Final outbox writes atomically apply known degraded-local charges, including cancellation and restart recovery; repeated writes and maintenance retries deduplicate that debt. Background maintenance reconciles queued events; restart marks interrupted dispatches uncertain and cancels undispatched tickets. During an authority outage, the leader uses the last acknowledged allocation, bounded by the scan's target, or its scan target with an explicit shared-accounting warning. Recovery reconciles outstanding events before coordinated admission resumes. Status exposes the latest admission coordination mode; session warnings remain a durable history, including earlier outages.

Authority changes are explicit. Pause participating scans, let active calls finish, and send `drain` to each participant using its host ID and current generation. Each leader flushes its outbox before acknowledging drainage. Then `freeze` on the authority returns the reconciled snapshot. `import` on the new authority and participating hosts installs that snapshot with the chosen owner and advances the generation. Resume only after those hosts have the new generation. Admissions from drained participants or stale owners are rejected; partitioned hosts never elect an authority.

Status and handover snapshots carry the most recent 128 reservations plus an omitted-history count. Scheduler debt, prices, observations, and per-scan deadlines are retained. The complete historical attempt ledger stays on the former authority; handover does not replicate that history.

Protocol 2.44 handovers retain each importing host's configured model prices and all history it already holds; bounded transfers never delete the former authority's complete ledger. Cancellation records a durable tombstone even when it arrives before admission. Rebuild participating hosts together for the added reservation aggregate-rate field. The accounting SQL schema remains version 1.

Disconnected usage reconciliation anchors both account and per-scan debt at reconciliation time when no authoritative reservation existed, preserving future deadlines and deduplicating retries. Admission and reconciliation reject incompatible group units before ledger mutation. For calls without a scan target, final and streamed pricing use the acknowledged account allocation to validate units; incompatible prices remain unknown, including during disconnected execution.

If neither a scan target nor an acknowledged allocation establishes account units, configured model prices alone do not establish account cost. Completed and interrupted calls retain token counts with unknown cost, including through restart and background reconciliation. These events retain the conservative unknown-cost pacing heuristic; they are not retroactively reinterpreted in the authority's units. Later calls with an acknowledged allocation resume estimates when their configured prices match those units.

Fresh exhausted-window observations defer new calls against that known account window until reset, including unpaced research and supporting calls. Account denomination persists independently of active rate leases and reservation history. Already admitted calls may finish. Missing or stale measurements retain best-effort continuation with a warning; observations for other named windows do not block admission.

Protocol 2.45 adds the typed `unit` field to accounting snapshots: currency, credits, or a named subscription window. Accepted admission requests (including queued requests) and reconciled usage establish it; cancellation receipts alone do not. Bounded status/handover keeps this field when all unit-bearing reservations are omitted. Imports validate unit syntax and retained history and cannot erase or change an importing host's established unit. Preserving denomination does not reactivate an expired pacing rate. Rebuild participating hosts together; the accounting SQL schema remains version 1.


## Stage 10 regression validation

Bundled handoff scheduler regressions use deterministic HTTP providers that obtain agent and artifact identities only from model-visible tool replies and inboxes. Component workflow tests separately cover missing-evidence returns, canonical findings, and independently executed patch/test artifacts. `patch_refs` and `test_refs` use the same publication and accepted-byte validation as other artifact-typed fields.

The default `beale-core` integration gate kills an active leader process and restarts the real host twice, checking normal maintenance recovery without provider redispatch. On Windows, the ignored `desktop_and_leader_process_restart_preserves_recovered_session` test additionally launches and terminates the executable selected by `BEALE_TEST_DESKTOP`; it checks process survival and recovered HTTP session detail, not visual UI interaction.

The ignored Windows `docker_windows_git_worktree_reaches_linux_worker_with_links_and_history` test captures a real linked Git worktree and sends it through the scoped worker gateway into Linux Docker. It installs Git only in its disposable Alpine fixture, then verifies executable/link semantics and self-contained history after the source repository has moved. This test setup is not automatic guest package installation by the product.

Storage defaults include real SQLite page-limit exhaustion and retry tests. The ignored Linux `enospc_preserves_artifact_and_worker_checkpoint_until_same_operation_retry` test requires a disposable container with a dedicated `--tmpfs /pressure:rw,size=1m`, writable `/tmp`, and the built `beale-storage` `swarm_files` test executable mounted read-only.
