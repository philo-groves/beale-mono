# v2

Desktop and app-server diagnostics are written to `logs/desktop.log` and `logs/app-server.log` beneath `BEALE_V2_HOME` or `~/.beale/v2`. Each file rotates at 5 MiB and retains three numbered backups. Startup prints the active log path; diagnostic messages also remain on stderr. Logs stay on the host and may contain local error paths, so review them before sharing.

Agent Feedback is an optional feature with one on-demand tool for agents to report observed Beale harness or runtime issues. Reports are appended as JSON Lines to the private app-server data directory at `agent-feedback.jsonl`, beneath `BEALE_V2_HOME` or `~/.beale/v2`. Each line includes the workspace, session, and agent IDs, issue kind, observation, optional workaround, and timestamp.

The optional Memories feature keeps the existing session transcript in the app-server's `state.sqlite` and stores extracted workspace entities and assertions in a separate local `memories.sqlite`. Completed main and subagent turns enter a durable host queue; the configured default small model processes them asynchronously. Four read-only agent tools search the current session, search memory records, read provenance and revisions, and traverse bounded graph neighborhoods. The feature is disabled by default; disabling it stops extraction and retrieval. The host-authenticated clear route removes one disabled workspace's memories without deleting transcripts.

A complete re-implementation of Beale using lessons learned from the first. This directory will be moved to the root and replace its content when it is ready.

The Rust workspace now includes `beale-agent-loop`, `beale-contracts`, `beale-core`, `beale-extender`, `beale-feature-api`, `beale-providers`, `beale-safety`, `beale-sessions`, `beale-storage`, `beale-tools`, and `beale-workspaces` under `apps/beale-app-server/beale-harness/`, plus the first Rune desktop client in `apps/beale-desktop-app/`. `beale-core` assembles the host; the session, workspace, and extension crates own their respective operations, using the shared host database for global records. Other app and extension directories remain reserved until their crate manifests exist. The workspace uses Rust edition 2024 and requires Rust 1.99.1, pinned in `rust-toolchain.toml`.

## Swarms and Fleet

Protocol 2.50 includes the explicit `beale_contracts::swarms` JSON contract (version 1) and host-owned durable state for the Swarms and Fleet implementation plan. Bounded decoders reject unknown fields, incompatible versions, and invalid configuration. Roles, profiles, assignments, execution attempts, container configurations, instances, and retained environments have separate identities. New-scan eligibility is checked separately from loading an existing scan's immutable definition, destination, provider-route, and leader-review snapshots.

`beale_storage::swarm_state::SwarmStore` initializes its own schema only when opened. It provides transactional queued-spawn acceptance, content-bound mutation receipts, checkpoints, handoffs, execution leases, tool-operation journaling, and lifecycle generation claims. Worker credentials are short-lived and stored as digests; authority comes from the saved scan, and a revoked or expired attempt cannot dispatch or renew. A replacement requires explicit confirmation that prior execution stopped. Database replay does not promise exactly-once external command execution. Resume, Keep, publication dependencies, and cleanup share the same transaction boundary; scan-end retention defaults to seven days with a 5 GiB storage reserve.

Fleet initializes its independent host coordination repository at app-server startup. Paired Tailscale origins and host-control credentials stay in the private host database, outside model projections. Account-budget groups use stable host-side account identity independently of rotating credentials, with generation-bound ownership and deduplicated usage events. These repositories are available without Desktop or optional Swarms initialization.

Stage 1 regression fixes preserve completed JSON `null` tool results and bind execution checkpoints and journal writes to a current, unexpired attempt inside their transaction. Ending a scan revokes all existing worker credentials and marks outstanding execution termination unconfirmed; reopening cannot revive those credentials. Host confirmation and publication/retention recovery remain explicit host operations. Environments registered after scan end inherit the persisted retention deadline. Registered pacing participants can replay identical acknowledged reservations after accounting handover, while new stale-generation requests and changed-content retries fail.

Swarms schema version 2 adds exclusive `(host, instance)` ownership across scans in the shared host database. Opening a version 1 store backfills claims transactionally; conflicting existing claims abort the upgrade and preserve the original state for inspection. Claims remain attached to retained private instances after execution stops. Fleet enforces physical release, reservations, and retained-instance ownership on the execution host. The JSON contract stays at version 1: tool completion state distinguishes a completed `null` result from unfinished work without changing the JSON representation.

Instance state is validated against its owning attempt: late Starting/Running reports cannot revive fenced or stopped execution, and termination-confirmed environments cannot contain live instance metadata. Repeated stop confirmations leave existing cleanup claims and lifecycle generations unchanged. The host-only `recover_operation` API reconciles an existing journal entry only after its original attempt is confirmed stopped. It can record uncertainty, or a known completion/cancellation with evidence references, while preserving original attribution and leaving worker credentials revoked. Recovery updates the journal, audit event, and content-bound acknowledgement in one transaction. It cannot create research operations, restart execution, change assignments, or overwrite known outcomes. This uses existing schema-2 tables and introduces no worker protocol operation.

Swarms and Fleet provide durable hierarchy state, local execution, private workspace snapshots, scoped peer worker routing, and Docker preparation/execution with owning-host resource reservations and retained-environment lifecycle management. The leader retains provider credentials and canonical research storage; worker artifacts are accepted centrally before handoff. Docker retains each agent's original container and private volume, verifies guest snapshot and artifact transfer before research, and requires confirmed whole-container termination before reuse. See the app-server README for portable runtime packaging and opt-in container tests. Selected scans use saved destination configurations and never fall back locally. Cross-host handoffs retain private edits and installed tooling, and canceled unclaimed allocations receive scan-end retention updates. New Scan exposes destination and account pacing controls; Fleet distinguishes saved image configurations, active instances, and retained environments. Pacing and RAM/storage admission are best-effort controls, not guarantees. Saving an image configuration alone does not select it for a scan. Existing Desktop connection files are not imported by the new host repository.

## Run the local desktop and app-server

Open two terminals in `beale-v2/`. Start the app-server in the first terminal:

```text
cargo run -p beale-core -- serve
```

Start the desktop in the second terminal:

```text
cargo run -p beale-desktop-app
```

On Windows, the running app-server shows the Beale icon in the notification area. Hover to see its running address, or right-click and choose **Exit** to stop the server and release its port. Ctrl+C in the server terminal also stops it.

The Settings sidenav shows the negotiated protocol version when the desktop validates the app-server's protobuf health response. To check the connection without opening the window, run `cargo run -p beale-desktop-app -- --check-connection`; it exits unsuccessfully if the host is offline or has an incompatible contract. Start order does not matter: the desktop retries every two seconds.

The top-right Canvas button opens an empty right pane that remains open when the desktop changes views, including the workspace surface network. Its icon is outlined when closed and filled when open. The pane takes up to half the window width while preserving room for the main content. Dragged network content stays within the main area beneath the side panes. On Windows, the button sits immediately left of Minimize.

In Settings → Providers, OpenAI uses the host Codex sign-in for subscription access or an API key; xAI, Anthropic, and Z.ai offer same-device subscription sign-in or an API key; OpenRouter uses API keys. OpenAI sign-in opens the official Codex CLI, Anthropic sign-in opens the official Claude CLI, and Z.ai sign-in opens ZCode Model Settings. Beale checks their official sign-in state without copying their subscription credentials. **Configure** sends a masked key to the local app-server; the desktop receives only whether the key is configured. **Forget** removes Beale-saved keys and supported provider credentials; Codex sign-in is managed by Codex. The **Custom** tab registers multiple OpenAI-compatible chat completions APIs by name, base URL, and model IDs, which can be discovered from `/models` or entered manually; each has an optional host-saved API key, lead/small defaults, and an opt-in OpenAI-compatible reasoning-effort control. Forget a saved key before changing that provider's API URL. Use `cargo run -p beale-desktop-app -- --provider-status` for built-in credential status without opening the window.

The Providers view loads available text models for configured built-in providers. OpenAI, xAI, Anthropic, and Z.ai maintain separate subscription and API-key catalogs and lead/small choices. Anthropic and Z.ai subscription catalogs currently contain selected models supported by their official CLIs; OpenRouter loads an API-key catalog. OpenRouter includes its automatic router and models that advertise tool and text support. Custom providers use the model IDs entered in their configuration, qualified by provider identity in sessions. The **Default Provider** control selects any configured built-in or custom provider; the first configured provider becomes lead automatically. Removing its last credential selects another configured provider. Catalog, default, and custom-provider operations require the same local control proof as credential operations.

For an Anthropic API key that is not scoped to one workspace, set `ANTHROPIC_WORKSPACE_ID` in the app-server environment before launch.

Subscription usage circles appear at the bottom of the icon rail when a provider reports a limit window. Hover for remaining percentages and reset countdowns. xAI uses the Beale subscription sign-in. OpenAI usage and subscription inference use the same Codex sign-in on the host; the tooltip names Codex as the source. The desktop refreshes usage every 20 minutes and after subscription status changes.

Open **Tracking** from the icon rail to view its dashboard. It plots subscription usage remaining over the past seven days from checks made while Beale runs, and daily stacked model usage for Beale research sessions. Switch the model chart between total call duration and provider-reported input plus output tokens. Main and subagent calls are recorded separately by role; calls without provider token counts contribute to duration but are excluded from token totals. Tracking starts collecting new history after the update and does not backfill earlier sessions or periods when Beale was closed.

Open **New Research**, select a workspace and an available model, enter a message, then press the send arrow. The app-server runs the selected provider's tool calls and saves turn activity locally. Sessions start with four base tools: `read`, `write`, `edit`, and `powershell` on Windows (`bash` on other hosts). The optional Webfetch feature adds one `webfetch` tool for web search and page text retrieval without JavaScript. Enable it in Extensions > Features and choose its workspace scope. The agent reads optional workspace guidance from `AGENTS.md` and recorded rules from `RULES.md`, alongside it. Beale maintains `RULES.md` from the workspace rules, including backfilling existing workspaces before a turn. Enabled, workspace-scoped feature tools are available immediately; the agent reads their guidance and installed plugin instructions from the supplied file catalog. The first response turns the draft into a session in the same view; its transcript appears above the composer. The draft workspace and repeat ribbon slides away when a session starts and stays absent for reopened sessions. Saved sessions appear beneath their workspace in the Home sidebar and can be reopened after a restart. The composer’s up and down buttons revisit sent messages from the current session and restore any unsent draft when moving past the newest message. Tool rows initially show a short description; expand one to fetch its arguments and a bounded output page. The command tool runs with the current user's host privileges, so use an externally managed VM or container when target code needs isolation. The Repeat control saves a job record after the first completed turn. Automations lists active, future, and past runs, and can skip the next occurrence or cancel the series. The app-server executes later occurrences in separate sessions while it is running. After downtime, one due occurrence runs and older missed occurrences are skipped.

Goal Mode is available from the New Research ribbon for each prompt. Selecting it lets the app-server continue the objective across turns, subject to optional turn and duration limits. Only active Goal Mode turns receive its `goal_status` agent tool and guidance.

New Scan names the selected workspace in its heading; click its name to switch workspaces. Enable **Swarms** in Extensions > Features to configure Basic Subagents, VDH VVS, OAI 948, or No Subagents. Selected Swarms execute locally through the host supervisor. No Subagents uses ordinary local research. Active scans retain their definitions and leader rules when Swarms is disabled. Safety displays the selected session rule read-only.

Each Swarm has one leader, research deputies, and bounded specialist worker profiles. Handoffs travel through parents. OAI 948 includes independent patch validation and progresses per work item. All definitions and profile instructions are snapshotted; changing a template or the new-scan feature toggle does not alter saved state. The retired Graph scheduler and sequential pipeline have no compatibility path.

Settings opens on Safety, with Auto-Review and Guardian tabs. The configured small model reviews `read`, `write`, `edit`, the host command tool (`powershell` on Windows, `bash` elsewhere), enabled feature tools (including `webfetch`), and plugin calls against three built-in rules: broad destructive changes, unrelated credential access, and recorded scope. After a denial, the session lead model can review the call once against two built-in Guardian rules. The plus button beside either rule-set title adds a rule to that stage. Each rule's name and description can be edited in a dialog, and each rule can be turned off; changes live in the host database and apply to subsequent tool calls. The catalog allows 16 rules in total. Review failures deny the call. With all Auto-Review rules off, those calls run without model review; agent surface writes remain Candidate. Reviews do not restrict host privileges or provide OS isolation.

The **Extensions** icon opens a separate sidebar with Features, Plugins, and Research Kits. Features opens by default. Plugins has All Plugins, Available, and Installed tabs; Installed filters the same plugin catalog. Four bundled Agent Plugins packages appear under Available as content-sized cards in the wide content area, and none are installed by default. Each card shows a three-line description and separate Skills, Tools, Resources, and Prompts stats. Bundled skill counts come from their package contents. MCP counts show an unknown marker until the plugin server can be started and queried; packages without an MCP server show zero. **Install** validates a bundled package and saves its installed state through the app-server; **Uninstall** clears that state and leaves the package available for reinstall. Installed reflects host-owned state across restarts. Installation does not yet load skills or MCP components into sessions. The plus button opens an external-source form, but source registration is not connected yet, so the form cannot submit.

Click **Quick Chat** beneath New Research to open a compact chat at the bottom right. Before sending, choose a registered workspace in the title ribbon or leave **No Workspace** selected for general chat. A selected workspace supplies its saved guidance, rules, and scope as context; Quick Chat has no file tools. Enter a message in the single-line composer and press Enter or the send arrow. The up and down buttons revisit messages sent in that chat and restore the unsent draft. The ribbon becomes the chat title when the first message is sent, and a bounded, scrollable transcript appears beneath it. The host uses the Default Provider, its configured source priority, and its lead model. Closing the panel ends the current chat; opening Quick Chat again starts a new one. Saved Quick Chats appear under Settings → Archive → Quick Chats, where Restore reopens the conversation in the dock. Archived workspace sessions appear in the Sessions tab and can be restored to the Home sidebar.

Both processes use `127.0.0.1:43831` by default. If that port is occupied, set `BEALE_V2_APP_SERVER_ADDR` to the same loopback IP and port in both terminals before starting them. For example, in each PowerShell terminal:

```powershell
$env:BEALE_V2_APP_SERVER_ADDR = "127.0.0.1:43832"
```

The server rejects non-loopback addresses. Local credential and session operations require a random control token stored in the app-server's private host directory (`~/.beale/v2` by default, or `BEALE_V2_HOME` in both processes). Host-wide workspace registration, sessions, and provider choices are stored in `state.sqlite` there. Standard harness components and optional features keep their own tables in the same database, created when compiled into the host. A `state.sqlite` from an earlier v2 development build is refused rather than upgraded; move it aside or delete it before starting a new build. Earlier v2 workspace, session, and provider setting files are not read; recreate any needed workspace and session and reselect provider choices after switching to the database. Before sending credentials, the desktop challenges the process on the loopback port to prove it knows that token. OAuth tokens and API keys remain in protected host files; on Windows, API keys are encrypted for the current user with DPAPI. Desktop appearance, window placement, and Fleet connection entries remain client-local files.

## Connect a remote app server over Tailscale

Install and sign in to Tailscale on the desktop and remote host. On the remote host, expose its loopback listener through Tailscale Serve HTTPS, for example `tailscale serve --bg --https=43832 http://127.0.0.1:43831`. Set `BEALE_V2_FLEET_HTTPS_PORT` on that desktop if Serve uses a different HTTPS port. In Fleet → App Servers on the remote host's desktop, open the QR button on the Local card and scan it with an authenticator app. The QR provisions a persistent Beale entry that produces six-digit codes every 30 seconds; keep it private. On another desktop in the same tailnet, click the plus icon and choose **Manually Add** to enter the remote MagicDNS HTTPS origin (for example `https://node.example.ts.net:43832`) and the current authenticator code. Choose **Tailscale Import** to list devices from the local Tailscale client, select an online device, set its Serve HTTPS port, and enter the same six-digit code. A listed device is not treated as a verified app server until pairing and descriptor checks succeed. The remote name defaults to its PC host name; a desktop-only display name can override it after connecting. The desktop checks the online same-tailnet peer, validates HTTPS and the protocol descriptor, then saves the connection in its private `desktop-fleet.json` file. Failed codes trigger exponential backoff on the remote host. Disabled entries remain saved and are not polled. App Servers has All, Available, and Enabled tabs; Virtual Machines has All, Running, and Not Running tabs. Virtual Machines lists Hyper-V guests from each reachable Windows app-server with host, state, source, and generation. Each card has an enabled toggle and workspace selector, plus a Can Run allowance icon. The allowance starts off and is saved on the owning app-server; VM inventory and settings remain owned by the connected app-server. Sessions still use the local app-server; its approved running Hyper-V guests can execute PowerShell commands through the optional `machine` argument.

For each guest to run commands, configure its Windows OpenSSH server and install the app-server user's public key for a guest account. On the app-server host, add a matching alias to that user's OpenSSH config, for example:

```sshconfig
Host beale-hyper-v-00000000-0000-4000-8000-000000000001
    HostName 192.0.2.10
    User ExampleUser
    IdentityFile ~/.ssh/beale_example_vm
    IdentitiesOnly yes
```

Use the guest's Hyper-V VM ID in the alias, not its display name. Verify and pin its SSH host key before running unattended sessions, and make the dedicated private key available to the app-server account without an interactive prompt. Enable **Can Run** and the intended workspace on the VM card. The agent receives the approved VM ID and name, then may set `machine` on `powershell`; SSH addresses and keys remain on the host. Guest commands run in the SSH account's directory and do not inherit the host workspace. This execution path does not start or stop VMs.
The app-server creates `SYSTEM.md` in that private host directory on startup. Edit its Markdown to change the base session prompt; the next turn reads the updated file. Future optional tool and plugin details can be appended at runtime without placeholder substitution.

Runbooks is an optional Feature, disabled by default. When enabled for a workspace, the agent can use `runbook_query`, `runbook_get`, `runbook_create`, `runbook_edit`, `runbook_run`, and `runbook_status`. Runbooks are workspace-owned documents in the app-server database with ordered Markdown and code cells. Every code cell has its own language identifier, so one runbook can hold multiple languages. Cells can have optional names of up to 40 characters; Canvas shows the name instead of the number in the cell header, and active Runbooks show it in progress text. Short runbook (`R1`) and cell (`L1`) IDs remain stable across edits. Edits require the current revision and a reason; supplying cells replaces the ordered list. The host retains revision snapshots. The authenticated `/v1/runbooks/query` and `/v1/runbooks/get` JSON routes use the shared `beale-contracts::runbooks` contract. A run executes supported Bash, Python, JavaScript, and PowerShell code cells in order in the workspace with the current user's host privileges. Each code cell starts a separate interpreter; Markdown cells are skipped, and execution stops at the first failure. Each cell has a 60-second limit, the whole run has a five-minute limit, and output is bounded. The status tool reads the saved result from the same session. Execution output remains a candidate artifact rather than verified evidence; use an external VM or container when isolation is needed. The session sidenav Runbooks hover menu lists recent Active, Prepared, and Done runbooks, showing live cell progress and update or completion times; each list expands beyond its first three entries. Canvas shows each cell's latest session output beneath its source, with stderr in red and the exit code on the Output row. The running cell's Play icon becomes a spinner, and a right-side cell status strip stays visible while the content scrolls.

Clicking a runbook in the session sidenav hover menu opens Canvas with its cells, current status, and per-cell results from that session. Open runbooks have closeable squircle tabs with a runbook icon and full title; switching tabs preserves each runbook's view state, and closing the last tab closes Canvas. Canvas content scrolls beneath the fixed tabs with a fade at the scroll edge. The Settings-style scrollbar runs along the right edge of the content area, to the right of the fixed cell status markers. A rounded border encloses the description and the metadata beneath it: runbook ID and status on the left, revision and update time on the right. Cells follow directly beneath the metadata, with any output attached to the cell that produced it. New runbook titles are limited to 64 characters, while unchanged older titles remain editable. Code cells show line numbers and syntax-colored source. Cell headers center the cell number and show Untouched for Markdown, Prepared for code awaiting a run, or a saved success or failure icon and time for code run in the current session. Each cell has a language selector and delete button. Code cells have a Play button for running only that cell; the host applies the session lock and Auto-Review before execution. Cell language changes and deletion save under the current document revision and clear that cell's saved result.

Tool calls use compact icon and label rows with a trailing disclosure chevron. Provider supplied reasoning summaries appear as muted lines in the transcript when available.

During a session turn, the desktop receives assistant text, available reasoning summaries, and each tool's start and finish over a framed HTTP response. The live activity sits below a “Working for HH:MM:SS” header. When the turn finishes, the header becomes “Worked for HH:MM:SS” with a chevron; the activity collapses while the final answer stays visible. Expanding the header reveals saved tool, reasoning, and intermediate text activity after a restart.

## Core Directories

### Apps

- `apps/beale-app-server/`: A general agent runtime server shared across app clients
- `apps/beale-desktop-app/`: An installable app client for Windows, macOS, and Linux
- `apps/beale-ios-app/`: An app client for iOS, not yet available on the App Store

### Extensions

- `extensions/features/`: Optional native features with deep app integrations
- `extensions/plugins/`: Optional skills and MCP servers using Agent Plugins 1.0
- `extensions/research-kits/`: Optional helpers to streamline certain programs

### Integrations

- `integrations/beale-for-codex/`: A third-party integration plugin for Codex
- `integrations/beale-for-claude-code/`: A third-party integration plugin for Claude Code
- `integrations/beale-for-cursor/`: A third-party integration plugin for Cursor

### Utilities

- `utilities/scripts/`: Scripts to assist with release, build, and other workflows
- `utilities/site/`: Basic utilities and assets for the beale.ai website
