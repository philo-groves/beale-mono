# Swarms definitions

`beale-swarms` supplies declarative workflows, profile snapshots, validated handoff contracts, and role-specific local hierarchy tools. The leader session harness coordinates saved Swarms; assigned native or Docker workers execute subordinate research. No Subagents continues to use ordinary local research.

`swarms.json` contains Basic Subagents (`basic`), VDH VVS (`vdh_vvs`), and OAI 948 (`oai_948`). Each definition has one coordinating leader, deputy profiles, worker profiles, permitted delegation, initial deputy intent, and directed handoff routes. Initial intent does not start processes. Basic permits multiple Research Deputies for distinct research areas. OAI 948 describes concurrent work items, with no sequential timer or global stage barrier.

`profiles.json` supplies stable specialist revisions and instructions. Mapper explores boundaries; Investigator develops hypotheses; Experimenter runs bounded checks; Challenger performs independent evidence-based scrutiny; Builder prepares reproductions, harnesses, and patches. Deputies inherit their stage responsibilities. The coordinator-only leader rule is saved with the definition; the host applies that rule during leader tool review and Guardian reconsideration.

All workflow handoffs go through parents. Workers submit to their deputy, then the leader resolves a destination deputy. A profile reference is not a sibling address. VDH VVS passes labeled candidates and evidence to Validation and returns assessments or requests for missing information. OAI 948 passes ranked targets, candidates, supported assessments, and remediation context; patches go back to Validation for independent checking and results return to Patch Generation and Reporter.

Handoff envelopes preserve task, scope, destination, record revisions, evidence/artifact references, observations, and unresolved questions. Specialized payloads require ordered target rankings, labeled claims, supported assessments, or patch/test references. Payloads cannot contain inherited conversation fields. A failed reproduction can be recorded as inconclusive without treating it as a refutation. Task completion never changes a finding status.

The host `SwarmStore` accepts pending handoffs, supports assigned/completed/blocked/canceled transitions, and checks immutable route/profile snapshots. Revision checks and content-bound operation receipts serialize transitions and retries. Parent assignment context is stored separately from original observations. These are trusted host APIs; the local supervisor and Stage 4 attachment pipeline enforce execution ownership and evidence-byte acceptance. Assigned workers route canonical operations to the leader through scoped credentials; inference and canonical records stay on the leader.

Custom definitions compose bundled profiles. Place a standalone definition in the app-server data directory's `swarm-templates/` folder; [example-review.json](examples/example-review.json) is synthetic. The host lists at most 64 files of up to 16 KiB each and ignores invalid files. Template IDs hash canonical definition content. Every new Swarm snapshots its definition, profiles, and leader rule; editing templates or disabling new Swarms does not change saved scans. A local selection does not initialize Swarms storage and cannot select Fleet destinations.

Saved bundled and custom views restore the complete snapshot independently of installed profile revisions. They retain saved topology, instructions, and leader rules, and never replace entries in the new-scan catalog. Separate saved revisions with the same definition ID can coexist. Desktop requires the matching snapshot for every saved Swarm; malformed snapshots and unsupported profile identities fail explicitly. Template validation requires leader, deputy, and worker profiles before catalog registration, matching scan creation.

Restored views own their metadata and use reference-counted handles. The cache retains at most 1,024 snapshots, refreshing recency on a hit and evicting the least recently used entry on insertion. This bounds cached views rather than the number of saved revisions that can be opened. Active callers keep their views through eviction; unused evicted views are released, and reopening rebuilds them from the saved snapshot. Invalid snapshots do not evict valid entries or change their recency.

The Graph crate, feature ID, peer scheduler, sibling messaging, sequential pipeline, and legacy-only Scout/Reviewer/Prover profiles are removed. There are no compatibility aliases or conversion readers. Retired development sessions are explicitly unsupported and left untouched. Client protocol 2.49 includes Swarm DTOs, the template route, and live/committed turn boundaries; retired sequential-timer field tags remain reserved. Update clients and servers together.

Run `cargo test -p beale-swarms` from `beale-v2/` for declarative workflow and durable handoff acceptance tests.

The five hierarchy tools list descendants, spawn a direct child, stop its branch, message a direct child, and message the parent with an optional handoff. Tool availability comes from saved host roles. The session harness supervises the saved hierarchy; durable inbox cursors and result receipts support suspension and resumed context without inference polling. Independent review starts with a fresh identity. Fleet tests queued acceptance before checkpoint release, including one-slot deputy suspension, competing allocations, and infeasible placement. Each subordinate owns a private writable copy. Selected Docker configurations are allocated by the harness, one agent per instance.

Local mailboxes retain the typed handoff envelope with its message, so the parent's next model turn sees routing, observations, and evidence references. Initial child prompts keep the original assignment alongside any early follow-ups. Swarm commands are bounded to 64 KiB of serialized input; prompt batching preserves unread messages when full handoffs would exceed a turn's input limit. Child completion summaries reserve mailbox bytes for the host prefix and truncate only at UTF-8 boundaries.

Transcript and supervisor checkpoint retries save the same completed turn up to three times, without repeating model inference or accepted tools. Exhaustion blocks the branch or stops a broken leader; accepted results remain durable. Provider recovery keeps the user stream open through the supervisor's final outcome. Assigned worker supervision additionally journals uncertain operations, retains candidate outputs, and reconciles lost transport or process ownership without blindly repeating effects.

Local provider failures after tool activity retry the same exchange, preserving accepted results. Repeated provider tool-call identities replay their original result within the execution; changed arguments fail explicitly. Exhaustion saves partial activity and blocks the affected branch without automatic tool replay. Ordinary messages retain their admission limit, while trusted lifecycle notifications can exceed it so a full mailbox cannot prevent execution release; all messages keep durable cursor-based acknowledgement. Recovery events use scan-wide sequence numbers across agents.

Workers receive their immediate parent's identity and the deputy's saved stage instructions in addition to their own specialist instructions. This context survives resume and feature disable and does not apply the leader-only coordinator rule to workers.

`swarm_materialize_artifact` is available for every Swarm role. Attach a local file as `file:relative/path` in finding artifact evidence or a handoff artifact field. The host records immutable bytes and producer/assignment provenance before accepting the finding or handoff. Explicit materialization creates a new file in the recipient's private directory; it never merges or overwrites another agent's edits. Storage acceptance does not verify a vulnerability claim.

Each new scan captures a sealed initial workspace snapshot. Subagents retain separate writable directories across related resumes; native file, command, runbook execution, and verification paths use their assigned copy. Snapshots exclude host state and credential paths, preserve supported metadata, and reject unsupported or changing inputs explicitly. Git histories are self-contained and exclude credential-bearing configuration; history containing excluded paths is rejected. File tests cover local directories, Windows-origin Git metadata, simulated platform rejection, and verified transfer. Real AMD64 Docker tests exercise Alpine/Ubuntu, retained reuse, cross-host restore, resource contention, and cleanup. Hyper-V allocation and native Arm64/macOS execution are not validated by those tests.


Protocol 2.49 adds `swarm_handoff` (`forward`, `complete`, `block`, `cancel`) and optional `swarm_spawn_subagent.handoff_id`. Forwarding carries the accepted envelope by ID through its permitted immediate-parent/direct-child route; observations, evidence IDs and source provenance are not re-encoded into 16 KiB message/task fields. Spawn can assign an owned handoff atomically, including to a fresh independent reviewer. The assigned owner completes work with a typed `WorkResult`; completion and evidence-backed assessment remain separate. The result is delivered to the immediate parent with the canonical envelope. Only the owner or its immediate parent can cancel; replacement of blocked work requires an inactive previous owner.

Handoff assignment, inbox delivery, typed results and retry receipts commit together. Bounded recovery leaves accepted work intact; exhaustion or finishing without an explicit result blocks unresolved owned handoffs. An explicit parent/operator message retries executor-blocked items and redelivers their accepted envelopes; unrelated inbox work does not reactivate them. Explicit handoff blocks remain blocked until a per-item forwarding or completion decision. Reassignment retires executable deliveries at the former owner and adds a custody correction to subsequent prompts without discarding saved context or upstream result notifications. Branch stop and scan end cancel unfinished handoffs while retaining completed results. Rebuild Desktop and participating app-servers/workers together for the model/peer contract.

Operator messages keep their exact user-facing text even when a claim includes recovery deliveries or custody corrections. Each claim consumes at most one operator message; subsequent messages remain unread for later turns. Local completion, coordinator interruption in new and existing sessions, and assigned-worker reconciliation preserve this separation after reopening storage. Host schema 2 adds nullable `session_turns.model_prompt` and leaves existing transcript rows unchanged. Model history reconstruction uses this host-only input to retain handoff context; client transcripts use the original operator text. The `swarm-local-workers` schema 3 binds each coordinator attempt to its committed transcript turn in the same transaction. Recovery appends an interruption notice only for an uncommitted attempt; it never overwrites or duplicates a completed turn. Recovery failures roll back the transcript, binding and lifecycle changes together. Coordinator completion also requires transcript preservation after checkpoint exhaustion. Failed writes stay pending for background maintenance, including already-stopped attempts. Terminal leader completion and recovery atomically record scan end and retention deadlines with transcript preservation and recovery completion. This includes successful completion once all executions and assignments have settled. Owner loss after the saved checkpoint or a failed scan-end write leaves finalization recoverable without repeating inference or replacing the saved answer. Cleanup still requires expiry, no Keep or active-use protection, acknowledged publications, and confirmed termination. Recovery cannot end a newer leader generation or re-end a reopened scan on replay. Protocol 2.49 is unchanged. Rebuild participating hosts/workers; earlier development in-flight turn formats remain unsupported without conversion.
